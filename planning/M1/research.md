## 0. TL;DR（先读这个）

**① 内核起点落锤 = (b) 长出 M0 内核**（不是 fork swift-markdown-engine）。M1 只要「源码样式化 + 分屏预览」，**不要混合渲染**（那是 M2）——源码样式化不过是 swift-markdown AST → NSRange 属性映射，标准 TextKit 2，进不了「岩浆池」。而 M0 已经交付了合规的薄封装（byte-exact、不碰 `.layoutManager`、智能标点全关）。把整个 pre-1.0、单人维护、AI 代写的 swift-markdown-engine 现在当内核，会把它「解析器统一管几何 + 标记隐藏 + 自带 per-document undo」的强意见栈塞进来——**这恰好和我们「源码为唯一真相 / AST 派生 / undo 入口在 L2」的契约打架**（验证 agent 抓出：单维度调研原本推 (a)，但『采用 (a) 又要 model 层 undo』自相矛盾，因为 swift-markdown-engine 自己持有编辑状态和 undo）。**swift-markdown-engine 改当 M2 上游**（同 TextKit 2 底座，M2 平移不是重写）；**CodeEditTextView 淘汰**（非 TextKit、自绘布局、为代码而非散文，选它 = M2 撕掉重来）。详见 [§14](#14-内核-spike-合成落锤)。

**② 5 个必须前置的 spike（一个人的整个风险预算就在这里，别边做边发现）**：
1. 内核 (b)-vs-(a)（淘汰 c）——同时**必须**在这一关钉死另外两件下游全都依赖的事：**undo 归属**（NSTextView 内建 undo vs 模型接管）与 **AST-as-API 缝的接口签名**。
2. **前景着色机制单一化**——源码样式化(§2)、专注变暗(§8)、rubric 光标行高亮(§10)三处各自提了**不同**机制（`NSTextContentStorageDelegate` 显示属性 vs `NSTextLayoutManager` rendering attributes vs 逐 run 上色）。**它们不可能同时对**（FB9692714：rendering attributes 在 macOS 26 重绘不可靠，Apple DTS 证实）。必须先 spike 出**一个**三处共用的机制。
3. **swift-cmark 是否公开暴露 C 版 HTML renderer**（`cmark_render_html` + GFM/footnote/sourcepos 扩展）——**预览 + 导出全押在它上面**（findings 3/4/6/11）。Apple 的 swift-cmark 历来只把 cmark 当内部 target 给 swift-markdown 用、不作公开产品。若为假，整条预览/导出管线要退回自写 `MarkupVisitor` 或打包 markdown-it。**看 Package.swift 的 product 可见性，别信 README。**
4. **FTS5 的 CJK 分词器**——默认 unicode61 对中文**零结果**（对核心受众是静默全崩，和 byte-exact 同级）。上真中文语料测召回，再说「搜索做完了」。
5. **TextKit 2 打字机 caret-rect**——大文件 `ensureLayout` 全量会卡秒级；只能局部。

**③ 已被证伪 / 必须改口的点**（对抗性验证的战利品）：
- 内核 finding「采用 (a) 且 model 层 undo」自相矛盾 → 翻成 (b)（见①）。
- **CodeEdit PR #2075 其实是 NSDocument 子类**、且用 **mtime 去重**（正是我们判定的反模式）——只能抄它的「重载语义」（把内容替换进现有 text storage 保住 TextKit2 订阅者、按 offset 保住选区、重载算一个可撤销帧），**别抄它的架构和 mtime 去重**；自写去重用 **SHA-256 内容哈希**做权威判据。
- `NSFileCoordinator(filePresenter:)` 的自写抑制**不是保证**（会双发、可能反而放松写互斥）——所以哈希做主、协调抑制只当第一道廉价过滤；回调必须幂等。
- **Highlightr 已停更**（README 自己跳转 HighlighterSwift）——违反我们「不引停更库」红线，`dependencies-and-licenses.md` 的 M1 approved starter 要**从 Highlightr 换成 HighlighterSwift**。
- 预览别用 `WKWebView.createPDF()`（整文档挤成一页）——用 `printOperation(with:)` + `runOperationModalForWindow`，且**必须先设 `op.view.frame`**。

**④ 两处必须按 PRD 拍死的矛盾**（不许留成 open decision）：
- **Mermaid**：finding 3 想为收紧 CSP/减体积把它踢出 M1，但 PRD §5.1 + finding 4 把它列为 M1 一等公民 → **按 PRD，M1 保留 Mermaid**（离线打包、CSP 门控、懒加载压体积）。
- **编辑区代码围栏高亮**：finding 4 要给编辑区加 HighlighterSwift（JSCore 整块重刷）、finding 2 的样式化只给「等宽 + 淡背景」不引这依赖 → M1 编辑区**先只做等宽+淡背景**（不引 JSCore 到编辑区），**代码高亮的「一等公民」体现在预览区**（highlight.js/Shiki）；编辑区增量高亮留到 M2 的 tree-sitter。

**⑤ 完备性批判补的 10 个盲区**已全部并入 `plan.md`：Agent 文件识别表、AST-as-API 缝设计、undo 归属、**文件树懒加载（10k+，与搜索不同的另一件事）**、前景着色单一 owner、frontmatter 基本显示、多文档/标签模型、设置持久化、无障碍（VoiceOver/全键盘/动态字体）、测试与验收基线。

**⑥ 排期**（critic 的 sequencing，已成为 `plan.md` 的 M1.0–M1.9 骨架）：Phase 0 内核+undo+缝 → Phase 0.5 三个并行去风险 spike（着色机制 / swift-cmark 可用性 / byte-exact 回归扩测）→ 1 源码样式化+Agent 文件识别+文件树+落盘+自动保存（**尽快能日用 = DoD**）→ 2 外部变更重载 → 3 语义/列表/图片（依赖 Phase 0 的 undo）→ 4 分屏预览+同步 → 5 omnibar+FTS5+命令面板 → 6 专注/打字机 → 7 版本历史 → 8 主题+导出（需 macOS 26 真机）→ 9 发布+Sparkle+Homebrew（但 **Sparkle EdDSA 私钥在 M1 一开始就生成并异地备份**、`SUFeedURL` 首个签名构建前就写进 Info.plist）。

## D1. Editor kernel starting point (a/b/c spike): fork swift-markdown-engine vs from-scratch NSTextView+TextKit 2 vs CodeEditTextView

**执行摘要.** Three candidates were re-verified against primary sources (July 2026). (a) nodes-app/swift-markdown-engine is Apache-2.0, v0.10.0 (2026-07-15), ~833 stars, 20 open issues, macOS 14+, actively developed by a small team (lead luca-chen198 plus several contributors, heavily AI co-authored, ~2-4 commits/week). It is the ONLY open candidate built on TextKit 2 that already does the M2 endgame: live source-styling WITH marker hiding and caret-reveal, driven by a single parser that "owns all geometry, marker/fence hiding, caret reveal, and incremental restyling," extensible via a MarkdownExtension protocol, split into three products (core / code-block / LaTeX) to control dependency surface. Risk: pre-1.0 churn (0.1.0 to 0.10.0 in ~3 months = rapid breaking changes), single lead, deep coupling. (b) From-scratch NSTextView+TextKit 2 gives full control, satisfies every red line natively, targets macOS 15 cleanly, and you already have the M0 skeleton — but building the M2 hybrid layer (custom NSTextLayoutFragment marker-hiding/caret state machine, stable viewport height) is the documented "lava pit" (est. 6-12 person-months from zero). (c) CodeEditTextView is MIT but deliberately does NOT use TextKit — it is a custom CoreText, line/code-oriented layout engine (v0.12.1, 2025-07-30; its parent CodeEditSourceEditor v0.15.2, 2025-09, is self-described "not ready for production"). Its README explicitly disclaims "right-to-left text, custom layout elements, or feature parity with the system text view." For a prose Markdown editor whose endgame is inline hybrid rendering (proportional fonts, variable line heights, inline images, marker reveal), (c) is code-first and actively boxes out M2 — choosing it means a rewrite at M2, the exact trap docs/09 flags for the SwiftUI-quick route. Cross-reference: MarkEdit (rejected TextKit entirely for CodeMirror-in-WKWebView) and CodeEdit (fled TextKit for custom CoreText after hitting perf walls even with STTextView) confirm that serious native editors distrust TextKit's defaults — but both are outside Colophon's already-decided native-TextKit editor core (route A).

**要避开的坑（前人教训）**
- Bear/Panda abandoned TextKit and wrote a C++ AST engine wrapped in native views (55ms to open the 94k-word Moby-Dick) — the top native team judged TextKit's default capabilities insufficient for high-performance hybrid rendering.　— _docs/09-tech-stack.md (Bear/Panda section)_
- CodeEdit built its own CoreText CodeEditTextView because, in their words, 'even with [Marcin's] great work [STTextView] we were hitting problems we couldn't optimize out, especially when loading large documents' — a flight from TextKit driven by unfixable large-document performance. This is the very library that is candidate (c).　— _https://mjtsai.com/blog/2025/08/15/textkit-2-the-promised-land/_
- MarkEdit rejected TextKit 1 and 2 outright for CodeMirror 6 in WKWebView, stating multi-caret editing and code folding are 'desperately hard' in TextKit and 'the community doesn't even have one single editor that can compete with CodeMirror or Monaco.' A cautionary data point on native TextKit hybrid difficulty — though it is route B, which Colophon already rejected for the editor core.　— _https://github.com/MarkEdit-app/MarkEdit/wiki/Why-MarkEdit_
- Marcin Krzyzanowski's 4-year TextKit 2 verdict (creator of STTextView): unstable scrolling, unreliable viewport height estimates (even Apple's TextEdit suffers), only NSTextContentStorage actually works despite the abstract interface, many self-filed bugs unfixed/unanswered, regressions common. This is the concrete shape of the 'lava pit' that from-scratch (b) and TextKit-based (a) both inherit.　— _https://blog.krzyzanowskim.com/2025/08/14/textkit-2-the-promised-land/_
- STTextView flipped from a permissive license to GPLv3 + commercial dual-licensing — a real precedent that licenses change. During THIS research a web-search summary even mis-reported swift-markdown-engine as MIT; the primary LICENSE confirmed Apache-2.0. Never trust cached/second-hand license claims — re-verify the LICENSE file on every dependency bump (dependencies §3.2).　— _https://github.com/krzyzanowskim/STTextView_
- Mark Text/Muya and SwiftDown stalled/were archived under single-maintainer bus-factor — directly relevant because (a) is single-lead + heavily AI-authored and (c)'s CodeEditSourceEditor is still 'not ready for production.' Bus factor is the dominant non-technical risk in kernel selection.　— _docs/09-tech-stack.md (Mark Text / SwiftDown sections)_

**要抄的做法（优秀实践）**
- Copy MarkEdit's split philosophy exactly: keep the editing core native and use the web engine only for what it is uniquely best at. For Colophon that maps to native TextKit editing + WKWebView strictly for preview/export/Mermaid/KaTeX (L4), never for editing state. MarkEdit also exposes its editor through a single stable API object and uses ts-gyb codegen to keep Swift/TS in sync — copy the 'one stable seam' idea for Colophon's L2 AST-as-API.　— _https://github.com/MarkEdit-app/MarkEdit/wiki/Why-MarkEdit_
- Copy swift-markdown-engine's seam design regardless of build-vs-adopt: a single parser that owns geometry, marker/fence hiding, caret reveal, and incremental restyling uniformly across built-ins and custom syntax via a MarkdownExtension protocol, plus a 3-product modular split (core / code-block / LaTeX) so you import only what you need and cap dependency surface (dependencies §1.2). If you build (b), mirror these seams so an M2 adopt-or-merge stays cheap.　— _https://github.com/nodes-app/swift-markdown-engine_
- Copy CodeEdit's performance-first mindset: lazy/viewport layout and line-based storage to load huge documents in milliseconds — and copy their candor (they publish explicit 'not ready for production' and limitation statements). Set concrete perf acceptance bars from competitors: MarkEdit opens a 10MB file near-instantly; Bear opens 94k words in 55ms.　— _https://swiftpackageindex.com/CodeEditApp/CodeEditTextView_
- For incremental syntax highlighting on the native side, reuse the ChimeHQ pattern (SwiftTreeSitter + Neon) that maps parse results to text attributes and computes invalidation ranges — this is the 'parse-result to TextKit attributes' middleware that a from-scratch (b) otherwise has to invent. Keep swift-markdown (Apple, Apache-2.0) as the full-AST/SourceRange semantic track for L3/L4/L6, per the dual-parser convention already in architecture.md §4.2.　— _docs/09-tech-stack.md (Neon / SwiftTreeSitter sections)_

**技术细节**
- Candidate (a): the closest match to Colophon's target. Built on TextKit 2, does live source-styling with marker hiding + caret reveal (M1 and M2 in one). Parser owns geometry/marker-hiding/caret-reveal/restyling; extend via MarkdownExtension; 3 products (editor-only zero-dep / code-block pulls HighlighterSwift / LaTeX pulls SwiftMath). Ships ARCHITECTURE.md + DocC. Fast churn: 0.1.0 to 0.10.0 in ~3 months.　（**nodes-app/swift-markdown-engine** · v0.10.0, 2026-07-15; ~833 stars; 20 open issues; team of ~5 (lead luca-chen198, heavy AI co-authoring), ~2-4 commits/week, actively maintained; pre-1.0 API unstable (pin exact version) · 许可: Apache-2.0 (verified against LICENSE, NOT MIT as one search summary claimed) · https://github.com/nodes-app/swift-markdown-engine）
- Candidate (c): deliberately bypasses TextKit — custom CoreText, line/code-oriented layout for large-file perf. README disclaims RTL, custom layout elements, and system-text-view feature parity, and points elsewhere for those. Uses TextStory + swift-collections. Syntax highlighting via tree-sitter in the CodeEditSourceEditor layer. Non-TextKit means it also sidesteps Colophon's TextKit-2 red lines but forfeits NSTextLayoutFragment-based hybrid render; code-first design boxes out M2 prose rendering.　（**CodeEditApp/CodeEditTextView (+ CodeEditSourceEditor)** · CodeEditTextView v0.12.1 (2025-07-30), 180 stars, 10 open issues; CodeEditSourceEditor v0.15.2 (2025-09-16), 708 stars, 39 open issues, self-described 'not ready for production' · 许可: MIT · https://github.com/CodeEditApp/CodeEditTextView）
- Candidate (b) reference stack, already in M0 research: construct manually NSTextLayoutManager -> NSTextContentStorage (addTextLayoutManager) -> NSTextContainer -> NSTextView(frame:textContainer:). Never read .layoutManager (silent TextKit-1 downgrade, still true on macOS 26). Instrument willSwitchToNSLayoutManager during dev to catch accidental downgrade. Source-styling for M1 = parse-driven attribute mapping; hybrid render for M2 = custom NSTextLayoutFragment + marker-hide/caret-reveal state machine + stable viewport height (the hard part).　（**AppKit NSTextView + TextKit 2** · Stable system API; WWDC22 remains the how-to; M0 skeleton already built · 许可: N/A (first-party code, Apache-2.0) · https://developer.apple.com/videos/play/wwdc2022/10090/）
- WWDC26 session 370 (targets macOS 27) adds new NSTextView extension APIs: NSTextViewportRenderingSurface, delegate methods to override viewport layout in subclasses, text-attachment reuse/caching, and easier line-numbers/collapsible-sections. Signals Apple is still investing in TextKit (mild long-term de-risk for (a) and (b)) — but these are macOS 27-only, must be #available-gated, and cannot be relied on at Colophon's macOS 15 baseline.　（**TextKit (macOS 27 / WWDC26 additions)** · Announced 2026; macOS 27 only · 许可: Apple SDK · https://developer.apple.com/videos/play/wwdc2026/370/）
- MarkEdit reference architecture: CodeMirror 6 (immutable EditorState + transaction updates, virtual scrolling) hosted in WKWebView (not Electron), wrapped in a genuine Cocoa shell keeping native menus/spellcheck/Writing Tools/inline predictions; JS<->Swift bridge via a global MarkEdit object + ts-gyb codegen; 4MB, handles 10MB files. Confirms route B feasibility but is outside Colophon's decided native editor core — use as lesson + the native-shell/JS-preview split blueprint, not as a kernel candidate.　（**MarkEdit-app/MarkEdit** · Actively maintained (2026) · 许可: App is GPL-3.0 (do not depend; read-only lessons) · https://github.com/MarkEdit-app/MarkEdit）

**M1 建议.** Spike (a) vs (b) head-to-head over ~1-2 weeks and ELIMINATE (c) early on architectural grounds, not code quality: CodeEditTextView is non-TextKit, code/line-oriented, "not production-ready," and explicitly excludes the custom layout elements and prose behaviors that M2 hybrid render requires — it delivers a fast M1 source editor but boxes out M2, forcing a rewrite (the docs/09 route-C trap). Between (a) and (b), both satisfy M1 (source-styling + split preview), so the tiebreaker is the M2 endgame and takeover cost. Recommended bet: treat (a) swift-markdown-engine as the reference/upstream and, if the spike's takeover test passes, adopt it via the dependencies §5 fork-and-pin-and-takeover conditions — it is the only candidate that already ships M1 AND M2 in one, and its pre-1.0/single-lead/AI-authored risk is exactly what §5 was written to contain. As a de-risking fallback, if the takeover test fails (you cannot confidently modify its marker-hiding/caret-reveal state machine solo+AI), build (b) a thin from-scratch TextKit 2 source-styling view for M1 — you already have the M0 bridge — while continuing to read (a)'s Apache-2.0 code as the design template, deferring the adopt-vs-grow decision to the M2 boundary so you never box out hybrid render. Either way, keep the Markdown source string as the single source of truth (AST derived), route undo through the L2 model, and keep the parser as a pure L3 producer — do NOT let any candidate's parser become the state owner. Non-negotiables to enforce during the spike: byte-exact round-trip must survive the styling layer; never read .layoutManager (audit (a)'s source; instrument willSwitchToNSLayoutManager); export/preview stays on WKWebView+PDFKit, never TextKit.

**⚔️ 对抗性验证：✅ 成立**（置信度 medium-high）

> Mostly holds, but the central "recommended bet" is over-tilted and internally contradictory. The structural spine survives scrutiny and matches primary sources: (c) CodeEditTextView is verifiably MIT, non-TextKit CoreText, code/line-oriented with disclaimed RTL/custom-layout/feature-parity, so eliminating it on architectural (M2-boxing) grounds is sound; the (a)-vs-(b) spike framing is reasonable; and the non-negotiables (byte-exact, never read .layoutManager, source-of-truth, model-layer undo, WKWebView/PDFKit for preview) are correct red lines. swift-markdown-engine is real, Apache-2.0 (verified via GitHub API, not the mis-reported MIT), TextKit 2, pre-1.0. The macOS-15 baseline is fine: the library is macOS 14+ and only gates Writing Tools to 15.1+, so no core editing API depends on macOS newer than 15. What does NOT hold is the recommendation's lean toward ADOPTING (a) as the load-bearing core: that bet is under-supported and partly self-contradictory, and the safer reading of the same evidence is the finding's own fallback — build (b) thin for M1, keep (a) as read-only design reference. Verdict: holds true, but the emphasis must flip from "adopt (a)" to "(b)-first, (a) as template," with the undo/state-ownership conflict elevated from a footnote to a gating blocker.

_质疑（skeptic 抓到的问题）_
- SELF-CONTRADICTION (strongest): The recommendation names 'route undo through the L2 model' and 'do NOT let any candidate's parser/editor become the state owner' as non-negotiables, then recommends betting on (a) as the core. Verified: swift-markdown-engine OWNS editing state and maintains internal, documentId-scoped undo history (confirmed in README). Its entire value proposition IS being the stateful editor. So 'adopt (a) AND keep L2 as the single source of truth with model-layer undo' is close to contradictory — adoption requires gutting and replacing the library's undo/state system, which is a re-architecture, not the incremental 'takeover' the finding implies.
- AI-authorship is a liability the finding scores as an asset. Commits are literally co-authored by 'Claude Opus 4.8' and 'Claude Fable 5' — the load-bearing marker-hiding/caret-reveal state machine is AI-generated code. The finding calls this 'AI-legible for takeover' (a plus). For a byte-exact-critical path, AI-generated complexity with latent bugs that even the lead may not fully own is a risk, not a de-risk. 'Reading the Apache-2.0 code as a template' inherits that same unvetted AI provenance.
- Bus factor is worse than reported. Verified: luca-chen198 wrote 170/228 commits (~75%); the repo has only 5 watchers/subscribers against 833 stars. High stars + near-zero watchers is a hype signal, not a maintenance/community signal. The finding cites SwiftDown/Mark Text single-maintainer collapse as a cautionary lesson, yet its recommended bet reproduces exactly that risk profile.
- Maturity understated. Repo created 2026-04-28 — under 3 months old (GitHub API). 13 releases with 0.1.1/0.2.0 shipped the same day it was created. Betting 'the product's most load-bearing component' on a <3-month-old pre-1.0 library is the very trap the finding warns about elsewhere.
- byte-exact (the single life-or-death red line) is UNPROVEN for (a): the README/docs are silent on BOM, line endings, trailing newline, and whitespace normalization while the library performs live marker/whitespace styling. The finding relegates this to a post-adoption 'test'; it should be a precondition to (a) even being a spike candidate.
- The '(a) ships M1 AND M2 in one' framing quietly imports (a)'s M2 architecture (parser owns geometry/marker-hiding/caret-reveal) — which is precisely the parser-as-state-owner pattern the red lines forbid. The thing that makes (a) attractive for M2 is the same thing that violates the architecture, so 'M2 in one' is not a free win.
- Whether .layoutManager is ever read in (a)'s source is unverified here (requires source audit); the finding correctly flags it but it remains an open blocker, not a checked box, before adoption.

_修正（据此改口）_
- Flip the recommended bet: default to (b) — a thin from-scratch TextKit 2 source-styling view for M1 on the existing M0 skeleton — and treat (a) swift-markdown-engine as READ-ONLY design/reference only. ## D2. Source-code syntax styling on TextKit 2 (M1): swift-markdown full-AST attribute mapping vs tree-sitter/Neon incremental highlighting, and how to apply attributes to a TextKit 2 stack without touching layoutManager.

**执行摘要.** For M1's "source styling" (headings larger, bold bolder, markers preserved but de-emphasized, plus the design-direction rubric: idle markers at ~35% ink, cursor-line markers full-strength terracotta), the winning approach is swift-markdown full-AST-driven attribute mapping with a debounced background reparse — NOT tree-sitter + SwiftTreeSitter + Neon. Rationale: (1) swift-markdown is already a mandated dependency (architecture §4.2 dual-track), is Apache-2.0, official, thread-safe/COW, gives exact SourceRange, and uses the cmark-gfm reference dialect where correctness matters — whereas tree-sitter-markdown's own maintainers state "it is not recommended to use this parser where correctness is important." (2) M1 styling is coarse (block + inline emphasis + marker de-emphasis), which is exactly what SourceRange gives cheaply; it does not need per-token semantic precision. (3) Neon's own author admits he has "not yet figured out a way to do [flicker-free highlighting] with TextKit 2, and it may not be possible without new API," and Neon v0.6.0's improvements center on TextKit 1 text-storage attribute application — so Neon buys us the least on the exact stack we are locked into. (4) Adopting tree-sitter would add three new dependencies (SwiftTreeSitter, Neon, a compiled tree-sitter-markdown grammar) plus its two-grammar (block+inline) quirk and non-incremental-for-inline reparse, for capability M1 does not use. Defer tree-sitter to M2/V1, where its real payoff is code-block language injection (per-language grammars) and mixed inline rendering. For applying attributes to the TextKit 2 stack without ever touching NSTextView.layoutManager (a hard red line — a mere read silently downgrades to TextKit 1), the reliable, Apple-DTS-blessed path is NSTextContentStorageDelegate.textContentStorage(_:textParagraphWith:) returning an NSTextParagraph carrying display attributes, refreshed via textLayoutManager.invalidateLayout(for:) — explicitly NOT NSTextLayoutManager.addRenderingAttribute, which Apple DTS has confirmed does not reliably redraw on update. Never blocking typing is handled by debounced background parsing (swift-markdown is a thread-safe value type), a Neon-style RangeInvalidationBuffer that batches invalidations, and viewport-scoped attribute application, with a large-file fallback (viewport-only styling above a measured size threshold, since swift-markdown has no incremental reparse).

Concretely: (1) On every edit, coalesce keystrokes and debounce (~100-150ms idle) a full swift-markdown parse on a background queue; the result is an immutable value-type AST. (2) Walk the AST (Visitor) once to build an attribute map keyed by UTF-16 NSRange derived from swift-markdown SourceRange — heading level -> font size step, strong/emphasis -> weight/italic, code spans/fences -> mono + subtle background, and the syntax markers ('#','-','>','*','`','[]()') -> the idle "marker.idle" ink@35% treatment. Refresh dynamically by calling textLayoutManager.invalidateLayout(for:) on affected paragraph ranges (the cursor-line rubric-red treatment: on selection change, invalidate the old and new cursor-line paragraphs so the delegate re-vends them with/without full-strength terracotta markers). Borrow Neon's architecture shape (decoupled token provider vs system interface + batched invalidation, optionally a fast per-line heuristic "phase 1" for instant feedback before the AST lands) without taking a Neon dependency. Reserve tree-sitter + Neon (both BSD-3, Apache-2.0-compatible) for M2 code-block language injection and mixed rendering, where their incremental, multi-language strengths actually pay off. _质疑（skeptic 抓到的问题）_
- ATTRIBUTION OVERCLAIM: The finding states 'Apple DTS confirms invalidateLayout(for:) re-triggers the delegate whereas invalidateRenderingAttributes(for:) does not.' In the actual thread, DTS confirmed only the addRenderingAttribute redraw bug and recommended the display-attribute path. The specific 'invalidateLayout re-triggers the delegate' claim came from a COMMUNITY developer (handle FossilCoder), not Apple DTS. This is exactly the mechanism the whole dynamic-styling refresh depends on, so it must be proven in the M1 spike, not treated as Apple-blessed.
- GLOSSED IMPLEMENTATION COST — marker-level ranges: Recommendation step (2) maps 'the syntax markers (#, -, >, *, `, []()) -> the idle marker.idle ink@35%' as if swift-markdown hands you marker positions. It does NOT. swift-markdown SourceRange covers the whole element (e.g. an Emphasis node's span); the individual delimiter characters have no addressable SourceRange. Marker offsets must be reconstructed from node boundaries, which is fiddly and correctness-sensitive for nested/mixed */_ emphasis, code-span backtick runs, reference/collapsed links, and setext headings (marker on a separate line). This is the crux of the de-emphasized-marker + cursor-line-terracotta rubric and the recommendation underplays it.
- UTF-8 vs UTF-16 mapping hazard (finding lists it but underweights it): swift-markdown SourceLocation is 1-indexed line + UTF-8 column; NSTextRange/NSTextView is UTF-16. Every parse pass needs line-start indexing plus UTF-8->UTF-16 translation. Mishandling multibyte/emoji/combining sequences yields misaligned styling AND, if that offset math ever informs an edit, a byte-exact-breaking correctness bug.
- PERFORMANCE tension in the delegate path for the DYNAMIC rubric: NSTextContentStorageDelegate re-vends attributes per WHOLE paragraph. The cursor-line terracotta rubric requires invalidateLayout on the old and new cursor-line paragraphs on EVERY caret move, forcing re-vend + relayout each keystroke/arrow press. Markdown prose commonly has very long soft-wrapped single-paragraph lines, so the 'avoids scroll jitter' framing is optimistic — it avoids storage-mutation jitter but introduces relayout-on-caret cost. openDecision (B) A/B must run BEFORE committing.
- PHASE-1 heuristic is speculative, not free: the 'instant per-line synchronous styling on keypress' idea directly conflicts with Neon's own finding that precisely-timed invalidation is 'extremely hard with TextKit 2.' A synchronous per-keystroke invalidateLayout risks the very flicker being avoided. Should be labeled experimental, not baked into the M1 responsiveness plan.
- SCOPE gap vs the review brief: the task asks about split preview and 60fps scroll sync. The finding is entirely editor-pane styling and says nothing about source<->preview scroll synchronization. No handwaving because it is simply out of the dimension — but the recommendation must not be read as covering scroll-sync; that remains an unaddressed M1 concern.
- LARGE-FILE feasibility is asserted, not measured: swift-markdown has NO incremental reparse (confirmed — whole-document each pass). The 'Bear 55ms Moby Dick' target is cited with zero measurement on target hardware, and the size-threshold fallback is left as an open decision. The whole large-file story rests on an unrun benchmark; the finding correctly calls this 'the single biggest M1 risk,' which itself signals the recommendation is not yet de-risked.

**待决（human call）**
- Confirm M1 excludes tree-sitter entirely and uses swift-markdown full-AST attribute mapping (architecture §4.2 lists this as an explicit M1 spike). Recommendation is 'no tree-sitter until M2', but this is a human sign-off point since it locks the M1 highlighting path.
- Choose the attribute-application mechanism in the spike: (A) NSTextContentStorageDelegate display attributes (recommended — reliable, byte-safe, no jitter, but re-vends whole paragraphs) vs (B) direct addAttributes to NSTextContentStorage.textStorage inside begin/endEditing (most reliable redraw, but can cause scroll jitter and needs care that attribute-only edits don't perturb layout). Decide after a jitter + perf A/B on real large files.
- Set the large-file threshold (in bytes/lines) above which styling degrades to viewport-only or coarse, since swift-markdown reparses the whole document per debounce with no incremental path. Needs measurement on target hardware (benchmark against Bear's 55ms Moby Dick bar).
- Decide the debounce window and whether to add a phase-1 instant per-line heuristic for zero-latency feedback before the AST pass lands, or accept a single debounced pass for M1 simplicity.
- Decide M2 posture: adopt Neon (BSD-3) for code-block language injection and mixed rendering, or hand-roll on SwiftTreeSitterLayer — given Neon's own weak TextKit 2 story, evaluate whether Neon's styler value survives on our stack.

**风险**
- swift-markdown has NO incremental reparse: every debounced pass reparses the whole document. On multi-MB files this can jank even off the main thread (map application still touches main). Mitigate with debounce + background parse + viewport-scoped attribute application + a size-threshold fallback. This is the single biggest M1 risk and the main argument the other way for tree-sitter.
- Red-line exposure: any accidental read of NSTextView.layoutManager silently and permanently downgrades to TextKit 1, killing all TextKit 2 styling. Neon's TextKit 1 system interfaces and much sample code touch layoutManager — if borrowing Neon/STTextView code, use only the content-storage/TextKit-2 path. Must be a code-review must-check and ideally a lint/grep guard.
- NSTextContentStorageDelegate re-vends attributes per whole paragraph; a pathological single huge paragraph (a very long line with no breaks, common in wrapped prose Markdown) is a performance cliff for both parsing-to-map and paragraph re-vending.
- SourceRange -> NSRange mapping mismatch: swift-markdown SourceLocation is line/column (byte-ish) while NSTextView/NSTextRange are UTF-16; mishandling multi-byte characters/emoji yields misaligned styling and, worse, wrong ranges — a classic correctness bug (SwiftTreeSitter documents the same UTF-8 byteRange vs UTF-16 range hazard).
- Building on addRenderingAttribute (the intuitive TextKit 2 API) would silently fail to update dynamic styling (Apple-DTS-confirmed) — a trap a solo dev + AI assistant could easily fall into; the recommendation explicitly routes around it.
- swift-markdown-engine, if used as a base, is pre-1.0 and single-maintainer (API churn); Neon main branch is 'not formally released.' Version-locking and read-don't-depend postures are required.
- Broader strategic risk (MarkEdit/CodeEdit/Runestone precedent): native TextKit 2 source styling is genuinely hard and multiple strong teams routed around it. If M1 styling perf/quality disappoints, the fallback is significant engineering (self-drawn layout in M2+), not a quick fix.

## D3. WKWebView split preview + 60fps bidirectional scroll sync (L4 preview subsystem for M1)

**执行摘要.** The whole preview subsystem can be built from battle-tested, license-clean pieces that already fit Colophon's L4 contract (Model→HTML one-way, preview never writes back). The source-to-HTML pipeline should reuse the cmark-gfm HTML renderer that ships inside swift-cmark (already a transitive dependency of swift-markdown) with CMARK_OPT_SOURCEPOS enabled: this emits a `data-sourcepos="startLine:col-endLine:col"` attribute on every block element for free, giving the exact source→DOM anchor map that VS Code, GitLab and others build by hand. swift-markdown itself has NO HTML renderer, so the choice is "cmark's C renderer" (fast, free sourcepos, dialect-matched) vs "a custom MarkupVisitor over the AST" (needed later for wiki-links/callouts/theming). For M1, use cmark's renderer for the body and keep the AST for semantics/outline/export. Serve the page through a custom WKURLSchemeHandler (not file://) so you can set a real strict CSP header, serve bundled KaTeX/Mermaid/Shiki offline, and keep `connect-src 'none'`. The scroll-sync "hard part" is a solved pattern: annotate blocks with source lines, collect the anchored elements, binary-search the two that bracket the viewport top, and LINEARLY INTERPOLATE the target line/offset between them; drive at 60fps by coalescing to one requestAnimationFrame per frame; break the feedback loop with a driver-ownership model (only the pane the user is physically touching emits sync) plus a short programmatic-scroll lockout — this is more robust than VS Code's leak-prone scrollDisabledCount. The genuinely native wrinkle is reading the top visible source line from the NSTextView WITHOUT touching layoutManager (a red line): use TextKit 2's NSTextLayoutManager / textViewportLayoutController to find the layout fragment at the visible-rect top and map it to a character offset → source line.

**要避开的坑（前人教训）**
- Abricotine gave its preview renderer nodeIntegration + broad local file access; rendering an untrusted .md became arbitrary local-file/JS access and the author abandoned the app rather than fix it. Colophon's preview must be powerless: no general file/exec/eval bridge, minimal single-direction messages, strict CSP, connect-src 'none'.　— _planning/standards/security-and-privacy.md §1 (docs/03)_
- KaTeX's auto-render extension relies on an inline onload handler, which forces `script-src 'unsafe-inline'` and breaks strict CSP for everyone who tried it (KaTeX issue #1968). Do not use auto-render; call renderMathInElement() from a bundled script after DOMContentLoaded.　— _https://github.com/KaTeX/KaTeX/issues/1968_
- VS Code's interpolation assumes each anchored block's rendered height is stable; collapsed <details>, images and multi-line table cells make the linear map drift (issue #175353). Rebuild the anchor map after async reflow (image load, fonts, KaTeX/Mermaid) — Joplin hit the identical async-image problem in PR #5512.　— _https://github.com/microsoft/vscode/issues/175353_
- VS Code's feedback-loop guard uses a scrollDisabledCount counter that, if mismanaged, 'continues to increase' and wedges sync. Prefer a driver-ownership + short lockout model where the echo is structurally impossible instead of counted down.　— _https://github.com/microsoft/vscode/issues/19459_
- Obsidian's community Sync-Scroll plugin works by monkey-patching private MarkdownView methods and 'may not work when you update Obsidian'. Build sync on a stable published contract (data-sourcepos) you control, never on internals.　— _https://github.com/XeroAlpha/markdown-sync-scroll_
- markdown-it-source-map (the obvious JS way to get data-line) is unmaintained — last publish ~9 years ago. Irrelevant to a native app anyway: cmark's built-in CMARK_OPT_SOURCEPOS supersedes it and is maintained with the parser.　— _https://www.npmjs.com/package/markdown-it-source-map_
- Mark Text/Muya (Electron, self-built web preview kernel) shipped data-loss bugs and is now archived (muya archived May 2026) — a warning that the preview/render kernel is a maintenance sink. Keeping preview a thin read-only downstream of the model (never a source of truth) is the safe posture, which Colophon's L4 contract already mandates.　— _docs/09-tech-stack.md §二 (Muya)_

**要抄的做法（优秀实践）**
- Copy VS Code's scroll-sync architecture verbatim: inject a source-line attribute on block elements, collect the anchored elements (getCodeLineElements), binary-search the two anchors bracketing the viewport top, and linearly interpolate the target line/offset (with a special multi-line branch for fenced code blocks where the marker sits on the inner <code>).　— _https://github.com/microsoft/vscode/blob/main/extensions/markdown-language-features/preview-src/scroll-sync.ts_
- Get the anchor map for free with cmark's CMARK_OPT_SOURCEPOS instead of hand-writing a source-map plugin; it stamps data-sourcepos (line:col-line:col) on every block element and is what GitLab standardized on for clickable/source-linked HTML.　— _https://gitlab.com/gitlab-org/gitlab-foss/-/merge_requests/23971_
- Follow MarkEdit's discipline: a genuine Cocoa app wrapped around a WKWebView — native NSToolbar/menus/spellcheck/Writing Tools, a typed JS↔Swift bridge (they use ts-gyb), zero telemetry, only-local assets. It proves a web-tech component can feel fully native and stay 4MB.　— _https://github.com/MarkEdit-app/MarkEdit/wiki/Why-MarkEdit_
- Copy Joplin's caching + invalidation: cache the line↔scroll-position map and recompute it when rendering/image loading is delayed, so sync survives async reflow. Their PR #5512 is the most complete open bidirectional implementation to read.　— _https://github.com/laurent22/joplin/pull/5512_
- Note Typora/Bear's endgame: a single unified inline-render pane eliminates scroll sync entirely. Split preview + sync is an M1 deliverable, but Colophon's M2 inline-rendering direction (swift-markdown-engine) will make this subsystem's sync burden shrink — so keep the sync code isolated and disposable.　— _https://www.slant.co/versus/2813/37045/~typora_vs_obsidian-md_

**技术细节**
- Parses to an immutable, thread-safe, copy-on-write AST with precise SourceRange (markup.range → SourceLocation line/column) — ideal for outline/semantics/export and for a custom data-sourcepos HTML visitor. Crucial gotcha: it ships NO HTML renderer; you must walk the tree yourself OR use the cmark renderer below.　（**swift-markdown (swiftlang)** · Actively maintained by swiftlang, tracks the toolchain (2026); DocC's parser · 许可: Apache-2.0 (compatible) · https://github.com/swiftlang/swift-markdown）
- The cmark-gfm C library underneath swift-markdown DOES expose cmark_render_html. Run it with CMARK_OPT_SOURCEPOS to emit data-sourcepos on all block elements, and WITHOUT CMARK_OPT_UNSAFE so safe-mode strips raw HTML and javascript: links. Same cmark-gfm dialect as the AST, so output matches; register matching GFM extensions (table/strikethrough/tasklist/autolink).　（**swift-cmark (cmark_render_html, CMARK_OPT_SOURCEPOS = 1<<1)** · Maintained by swiftlang on the gfm branch (2026), transitive dep of swift-markdown · 许可: BSD-2 (compatible) · https://github.com/github/cmark-gfm/blob/master/src/html.c）
- Math rendering. Bundle locally and offline (R1.1). Do NOT use auto-render (inline onload breaks CSP); call renderMathInElement() from your bundled script post-DOMContentLoaded. Self-contained, no deps, synchronous — good typing feedback. Keep current: CVE-2025-23207 was fixed in 0.16.21.　（**KaTeX** · v0.16.47, last published May 16 2026; active · 许可: MIT (compatible) · https://katex.org/versions）
- Diagram rendering. Must run securityLevel:'strict'; historically wanted 'unsafe-eval' for some layouts, so isolate it or gate behind a feature flag. Multi-MB bundle → first-paint cost. CVE-2026-41907 noted but Mermaid states it does not use the vulnerable code path.　（**Mermaid** · v11.13.0; very active (2026) · 许可: MIT (compatible) · https://github.com/mermaid-js/mermaid/releases）
- Preview-side code highlighting with VS Code-grade accuracy. Default Oniguruma engine is WASM → requires script-src 'wasm-unsafe-eval', weakening CSP; v3 offers a pure-JS RegExp engine (@shikijs/engine-javascript) that avoids the WASM concession. Preview-only; editor highlight is a separate native track.　（**Shiki** · v3.x; active (2026) · 许可: MIT (compatible) · https://github.com/shikijs/shiki）
- Serve the preview through a private scheme handler rather than file://: lets you set a REAL strict CSP response header, serve bundled assets, keep connect-src 'none', and avoid granting file:// read access to user folders (better sandbox posture, R1.1/R2.3). Pair with WKContentWorld to isolate the bridge (R1.5) and a non-persistent WKWebsiteDataStore.　（**WKURLSchemeHandler + WKContentWorld (WebKit)** · Stable system API (macOS 15 target) · 许可: Apple SDK · https://developer.apple.com/documentation/webkit/wkurlschemehandler）
- To read the top visible SOURCE LINE from the editor for editor→preview sync WITHOUT touching NSTextView.layoutManager (a hard red line — a mere read silently downgrades to TextKit 1): use NSTextLayoutManager.textViewportLayoutController / enumerateTextLayoutFragments over the visible rect to get the fragment at the top edge, take its range start, convert to a character offset, and map offset→line via a cached line-start index. Same API scrolls the editor back for preview→editor.　（**TextKit 2 NSTextLayoutManager / NSTextViewportLayoutController** · Stable; TextKit 2 (macOS 12+); viewport height still estimated so guard for jitter on huge docs · 许可: Apple SDK · planning/standards/architecture.md §6 (docs/09)）
- data-sourcepos value format is startLine:startCol-endLine:endCol; block-level only (fine for line-granularity scroll sync). Parse startLine into your anchor array. Watch the known cmark/markdown-it quirk that list end-rows include trailing blank lines.　（**CommonMark sourcepos convention** · Stable convention (cmark, GitLab, VS Code) · 许可: n/a · https://github.com/microsoft/vscode/pull/134799）

**M1 建议.** M1 concrete build:

PIPELINE (L4, Model→HTML one-way):
1. Body HTML: call cmark-gfm's `cmark_render_html` via swift-cmark with options = CMARK_OPT_SOURCEPOS | (safe mode, i.e. do NOT set CMARK_OPT_UNSAFE) and register the GFM extensions that match the swift-markdown parser (table, strikethrough, tasklist, autolink). CMARK_OPT_SOURCEPOS stamps `data-sourcepos` on every block element — this IS your anchor map, no custom plugin needed. Safe mode already strips raw HTML/`javascript:` links, satisfying R1.2's first line of defense; add a Swift-side sanitizer pass only if you later opt into a raw-HTML subset. Keep the swift-markdown AST for outline/frontmatter/export structure (it is the semantics track per architecture §4.2); a custom MarkupVisitor emitting data-sourcepos (read `markup.range` → SourceLocation.line) is the fallback ONLY when you need custom syntax (wiki links, ==highlight==, callouts) that cmark can't render — defer that to when those features land.
2. Delivery: register a WKURLSchemeHandler for a private scheme (e.g. `colophon-preview://`). It serves (a) a fixed shell HTML with the bundled JS/CSS and the strict CSP as a real response header, and (b) the rendered body injected as a DOM text/HTML node via postMessage — never via evaluateJavaScript string-concat of content (R1.5). This beats loadFileURL(allowingReadAccessTo:) because you set a genuine CSP header, get a stable custom origin, and never grant file:// read access to any user directory.
3. WKWebViewConfiguration: non-persistent WKWebsiteDataStore; a dedicated WKContentWorld for the bridge so page content can't reach it; navigationDelegate cancels every navigation except the initial load and routes external links to NSWorkspace.open; disable javaScriptCanOpenWindowsAutomatically; keep JS enabled (KaTeX/Mermaid need it).
4. CSP (M1 spike to finalize, but target): `default-src 'none'; connect-src 'none'; object-src 'none'; frame-src 'none'; base-uri 'none'; img-src 'self' data:; font-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'`. Reality checks from research: KaTeX auto-render uses an inline onload handler that forces script 'unsafe-inline' — do NOT use auto-render; call `renderMathInElement()` from your bundled script after DOMContentLoaded to keep script-src at 'self'. KaTeX/Mermaid inject inline STYLES, so style-src almost certainly needs 'unsafe-inline' (acceptable; style injection is low-risk). If you ship Shiki, its Oniguruma engine is WASM and needs `script-src 'wasm-unsafe-eval'` — or use Shiki v3's pure-JS regex engine to avoid that. Mermaid must run at securityLevel:'strict'.

SCROLL SYNC (60fps, bidirectional, no feedback loop):
Anchor model (copy VS Code): every synced block has data-sourcepos → parse startLine into a sorted array of {element, startLine, endLine, top(), height()}. Rebuild this map on each preview refresh AND after async reflow (image `load`, web-font load, KaTeX/Mermaid completion) via a ResizeObserver — stale heights are the #1 drift cause (Joplin, VS Code <details>/image bugs).

Editor→Preview: on NSScrollView boundsDidChange (coalesced to at most one action per frame), compute the top visible SOURCE LINE from TextKit 2 WITHOUT layoutManager: use NSTextLayoutManager.textViewportLayoutController (or enumerateTextLayoutFragments over the visible rect) to get the fragment at the top edge, take its range start, convert to a character offset via the content manager, map offset→line via the Document's cached line-start index, and compute a fractional progress within that fragment. Push {line, fraction} to the webview. JS (inside requestAnimationFrame): binary-search the two anchors bracketing `line`, interpolate targetY = prevTop + progress*(nextTop - prevTop) where progress = (line - prevStartLine)/(nextStartLine - prevStartLine), and window.scrollTo(targetY).

Preview→Editor: on webview scroll (throttled to one rAF per frame), run the inverse of VS Code's getEditorLineNumberForPageOffset: binary-search anchors bracketing the viewport-top Y, interpolate the source line (linear between the two anchors; for multi-line code blocks interpolate within [startLine,endLine] using content-area progress). postMessage {line, fraction} to Swift; Swift scrolls the NSTextView so the layout-fragment frame for that line's start (obtained again via NSTextLayoutManager, never layoutManager) sits at the viewport top.

Feedback-loop prevention (better than scrollDisabledCount, which VS Code found leaks): a DRIVER-OWNERSHIP model. Detect the physically-active pane from user-intent events — scrollWheel/magnify/gesture on the native side, wheel/touchstart on the web side — and mark it the driver for a ~150ms sliding window. Only the driver emits sync commands; the follower's programmatic scroll is applied while an `isApplyingSync` flag is set, and the follower's own scroll handler early-returns whenever that flag is set OR it is not the current driver. This makes the echo impossible instead of merely counting it down.

60fps discipline: never call evaluateJavaScript per scroll tick (async, cross-process, will stutter). Coalesce every scroll signal to a single per-frame update carrying only the LATEST value, and do the actual DOM scroll inside the webview's requestAnimationFrame. Prefer postMessage of the target value + a JS rAF that eases toward it over synchronous evaluateJavaScript.

Sequencing suggestion: M1 = split preview with KaTeX + code highlight + this sync. Consider deferring Mermaid and Shiki-WASM to a later M1 point (or M2) to avoid the unsafe-eval/wasm-unsafe-eval CSP concessions and the multi-MB bundle on first paint — a human call (see open decisions).

**⚔️ 对抗性验证：✅ 成立**（置信度 medium-high）

> The recommendation HOLDS with material caveats. Its architecture is standard-of-the-industry and, importantly, respects every M1 red line: preview is read-only (source-of-truth and byte-exact saves untouched), it routes editor-position reads through NSTextLayoutManager and explicitly never touches NSTextView.layoutManager, and it does not affect model-layer undo. Split preview + 60fps bidirectional sync IS in-scope for M1 (ROADMAP §3.1 / M1 overview A), and hybrid inline rendering stays in M2 as required. All named APIs exist on the macOS 15 target and all core dependencies are license-clean and maintained. However, three claims are oversold and need correction: (1) the "reuse cmark's HTML renderer for free via swift-markdown's transitive dependency" pitch is not accurate; (2) the 60fps-on-large-docs confidence understates a documented TextKit 2 defect; (3) a few version/status details are stale. None of these break the approach — they change the build plan and the risk framing, so the verdict is holds=true with corrections rather than a refutation.

_质疑（skeptic 抓到的问题）_
- cmark 'for free / already a transitive dependency of swift-markdown / dialect-matched, no custom plugin needed' is misleading. Verified: swift-markdown vends only the `Markdown` product and does NOT re-export the `cmark-gfm`/`cmark-gfm-extensions` C products — you cannot `import cmark_gfm` from it. To call cmark_render_html you must add a SEPARATE direct dependency (swiftlang/swift-cmark or a wrapper like stackotter/swift-cmark-gfm), which introduces the well-documented 'multiple targets named cmark-gfm' duplicate-target conflict and requires manual GFM extension registration (cmark_gfm_core_extensions_ensure_registered + attach table/strikethrough/tasklist/autolink). The 'dialect-matched' guarantee only holds if you pin the EXACT swift-cmark revision swift-markdown uses and re-verify on every bump — an ongoing maintenance burden the finding omits.
- The pipeline recommendation fights the project's own two-track-parse contract. architecture.md §4 already mandates the swift-markdown AST as the semantic source of truth ('两轨都从同一份源码字符串派生'). Adding cmark_render_html creates a THIRD independent parse of every document (tree-sitter highlight track + swift-markdown AST + cmark HTML), not a reuse of the AST as implied. Since a custom MarkupVisitor can emit data-sourcepos directly from the swift-markdown SourceRange (markup.range -> line) the finding already relies on for outline/export, the 'defer the visitor to when custom syntax lands' advice is weaker than presented — the visitor also avoids the second cmark dependency, the duplicate-target conflict, and dialect skew.
- 60fps bidirectional sync is presented as a 'solved pattern', but the editor->preview leg depends on reading the top visible line from TextKit 2, which has a DOCUMENTED layout defect: NSTextLayoutManager fails to update layoutFragmentFrame after edits (Apple engineer-confirmed; reported ~600px frame errors) and uses estimated document height for viewport layout. On large documents this makes the top-line reading jitter or jump. The finding lists this as a risk but still headlines '60fps... solved' — the smoothness claim is genuinely at risk on the exact large-file case M1 must survive, and no mitigation beyond 'guard for jitter' is offered.
- data-sourcepos is block-level only, yet the recommendation describes linear interpolation WITHIN multi-line fenced code blocks 'using content-area progress'. cmark sourcepos gives startLine:endLine for the block, not per-visual-line anchors, so interpolation inside a block assumes uniform line height and breaks under soft-wrap / variable-height rows — the same drift class it warns about between blocks.
- Minor staleness: Shiki is described as 'v3.x' with a 'v3 pure-JS regex engine'; current is v4.0.1 and the @shikijs/engine-javascript package is the maintained pure-JS engine (MIT, avoids wasm-unsafe-eval) — the mechanism is correct, the version label is out of date. KaTeX/Mermaid CVE specifics (CVE-2025-23207, CVE-2026-41907) and Mermaid securityLevel:'strict' behavior were not independently re-verified here; they affect only the deferrable KaTeX/Mermaid/Shiki layer, not the core verdict.

_修正（据此改口）_
- Rewrite the pipeline dependency plan: state plainly that cmark_render_html requires a NEW direct SPM dependency on swiftlang/swift-cmark (or a thin wrapper), pinned to the SAME revision swift-markdown resolves, with the duplicate-target conflict resolved by ensuring the whole graph shares one swift-cmark. Re-check its BSD-2 license and revision on every swift-markdown bump (per dependencies-and-licenses.md). Do NOT describe it as free/transitive.
- Treat 'cmark C renderer vs custom MarkupVisitor' as a near-even call for M1, not a settled recommendation. Given the architecture already parses to a swift-markdown AST for the semantic track, a MarkupVisitor emitting data-sourcepos reuses that single parse, avoids the second cmark dependency and its target conflict, and keeps dialect authority in one place. Recommend a small spike comparing (a) cmark render vs (b) AST visitor on real docs before committing — align this with the D1 kernel-start spike rather than pre-deciding cmark.
- Downgrade the 60fps claim to 'target, pending large-doc validation.' Add a concrete mitigation for the TextKit 2 fragment-frame/estimated-height defect: prefer stable scroll anchors (character-offset -> fragment) over absolute Y, force .ensuresLayout when reading the top fragment, and add a large-document (10k+ line) sync-smoothness test to the M1 test matrix, since the documented bug bites exactly there.
- Constrain intra-code-block interpolation to block granularity (snap to block start/end) unless a per-line anchor scheme is added; do not claim smooth interpolation inside wrapped multi-line blocks from block-level sourcepos alone.
- Update library status: Shiki current is v4.x with @shikijs/engine-javascript (MIT) as the CSP-safe engine; KaTeX and Mermaid CVE/securityLevel notes should be re-verified at implementation time. Keep Mermaid + Shiki-WASM deferral flagged as an open decision, but note it mildly conflicts with ROADMAP §3.1 which lists Mermaid + code highlighting as M1 first-class features — resolve that as an explicit human scope call, not silently.

**待决（human call）**
- HTML generation path: cmark's C renderer (fast, free data-sourcepos, dialect-matched, minimal code) vs a custom MarkupVisitor over swift-markdown (full control, needed anyway for wiki-links/callouts/==highlight==/theming and export). Recommendation is cmark for the M1 body and defer the visitor — but confirm, since custom syntax may arrive early.
- Scope of M1 render enhancements: ship KaTeX only in M1 and defer Mermaid + Shiki-WASM? Doing so keeps CSP at script-src 'self' (no unsafe-eval/wasm-unsafe-eval) and avoids a multi-MB first-paint bundle. Human call on the feature/security/size trade.
- Exact CSP string, specifically whether style-src must include 'unsafe-inline' (KaTeX/Mermaid inject inline styles — almost certainly yes) and whether Shiki forces 'wasm-unsafe-eval' or you adopt its JS engine. This is the deferred item #1 in security-and-privacy.md §5.
- Sync feel: continuous interpolation (VS Code-style, matches viewport top exactly) vs caret-anchored (keep the block at the caret aligned, less jitter while typing). Continuous is the default recommendation; validate with dogfooding.
- Preview update model for M1: full debounced re-render on edit (simple, correct) vs incremental DOM patching (smoother but complex). Recommend full re-render for M1; revisit if large-doc reflow stutters.

**风险**
- TextKit 2's estimated document height / viewport layout (a documented instability, docs/09) can make the editor→preview top-line reading jump on large documents, degrading sync smoothness. Mitigate with stable scroll anchors and by mapping via layout fragments rather than absolute Y.
- Cross-process evaluateJavaScript on every scroll tick will miss 60fps (async, IPC). Mitigation is mandatory: coalesce to one per-frame postMessage carrying only the latest value, scroll inside the webview's requestAnimationFrame.
- Async reflow — images, web fonts, KaTeX, Mermaid, Shiki — invalidates cached element offsets and causes drift (VS Code, Joplin both hit this). Must rebuild the anchor map on load/ResizeObserver events; easy to forget and hard to notice until a user reports drift.
- Mermaid ('unsafe-eval' historically) and Shiki (WASM 'wasm-unsafe-eval') pull against the strict CSP red line (R1.3). Every concession widens the preview's attack surface for untrusted/agent-authored .md; isolate, gate, or defer.
- Variable-height blocks (collapsed details, tables, images) break the linear-interpolation assumption between anchors, producing visible misalignment (VS Code #175353). Line granularity plus frequent map rebuilds limits but does not eliminate it.
- Bundle size / first-load latency: Mermaid + Shiki add several MB and WebView init cost, hurting perceived startup on a product whose pitch is 'native, light, fast'. Lazy-load heavy renderers only when a diagram/code block is present.
- Bridge/feedback-loop bugs are subtle: a mis-scoped driver window or a leaked isApplyingSync flag reintroduces the infinite loop. Needs deterministic tests (simulate driver handoff and echo suppression).

## D4. GFM suite, LaTeX, Mermaid, first-class code highlighting

**执行摘要.** The four features split cleanly along the architecture's editor/preview seam, and 2026 research surfaces one gap that must not surprise us mid-M1. GFM: Apple's swift-markdown (Apache-2.0, v0.8.0 May 2026) natively parses GFM tables, task-list checkboxes, and strikethrough as first-class Markup node types, but it ships with cmark-gfm's footnote extension DISABLED (CMARK_OPT_FOOTNOTES off) — footnotes are the one GFM-suite element the AST will not see (swiftlang/swift-markdown#115). LaTeX: for M1 (which is source-styling, not inline hybrid render — architecture.md §4.2), math stays as source text in the editor and is rendered by KaTeX (MIT, active) in the WKWebView preview; native inline rendering via SwiftMath (MIT, actively maintained 2026, CoreText, macOS 15+) belongs to M2's inline-render work, not M1. Mermaid (MIT, v11.16, active) only runs in a webview and is bundled offline. Code highlighting must be split: the preview area gets a bundled JS highlighter (Shiki for VS-Code-quality, or highlight.js for weight), while the editor area's fenced code blocks need a native highlighter. The most important dependency correction: Highlightr — which the current dependencies-and-licenses.md lists as the approved M1 starter — became UNMAINTAINED in 2026 and its own README now redirects to HighlighterSwift; under the standards' own §1.2 hard gate (no abandoned libs), the approved starter should switch to HighlighterSwift (MIT, active, highlight.js 11.11.1), with tree-sitter + Neon as the M2 incremental-highlight upgrade. MarkEdit-preview gives a directly copyable pattern: one webview bundle of markdown-it + KaTeX + Mermaid + highlight.js (~5MB full / 250KB lite).

## D5. Markdown semantic shortcuts and smart list behavior

**执行摘要.** Colophon's editor is AppKit NSTextView + TextKit 2 with swift-markdown, NOT CodeMirror. So MarkEdit and CodeMirror are logic references, not code we can drop in: their well-tested algorithms (list continuation, renumber, markup-backspace, toggle wrap/unwrap) should be PORTED to Swift as pure transforms on the source string. Every semantic command (bold/italic, heading up/down, toggle checkbox) and smart-list behavior (Enter continues, Tab indent/dedent, empty item exits, ordered renumber) reduces to one primitive: replace a source substring and set a new selection. That primitive must be the single choke point where (a) undo is registered on the Document's UndoManager in L2 (architecture §5), (b) byte-exactness is preserved (inserted newlines match the document's LF/CRLF style; indentation respects the existing whitespace convention; BOM/trailing-newline untouched — architecture §3.2), and (c) coalescing is broken so the command is its own undo step, not merged into the user's typing group. The AST (full swift-markdown track) is used only to READ block context (is this a heading? an ordered item at index N? a checkbox item?); edits are computed on and applied to the source string, which stays the single source of truth. CodeMirror's insertNewlineContinueMarkup / deleteMarkupBackward / renumberList encode the exact edge cases we need and are the best blueprint; swift-markdown's ListItem.checkbox and SourceLocation give structure lookup but require careful UTF-8→UTF-16(NSRange) offset translation. Keep M1 single-cursor (Joplin's multi-cursor smart-list pain). Never touch NSTextView.layoutManager and never rely on NSTextList (broken since macOS 14) — our commands are pure text, so list indentation is literally spaces in the source, which is both byte-exact-friendly and TextKit-2-safe.

**要避开的坑（前人教训）**
- Editing NSTextView/UITextView textStorage DIRECTLY bypasses the view's undo tracking and can even invalidate the PRIOR typing undo step — a developer found that type→emoji-insert→undo removed the emoji but then could not undo the typing. Fix: bracket every programmatic edit in shouldChangeText(in:replacementString:) … didChangeText(), or register your own inverse undo in L2. Never mutate textStorage raw.　— _https://developer.apple.com/forums/thread/730221_
- Run-loop undo coalescing silently merges a programmatic edit made in the same run-loop pass as typing into the SAME undo group, so one Undo reverts both. A semantic command (e.g. toggle bold) fired mid-typing gets swallowed. Fix: call breakUndoCoalescing() to force a group boundary before the command.　— _https://christiantietze.de/posts/2022/09/undoable-text-changes/_
- Joplin had to DISABLE its smart list-insert logic when multiple cursors are active because tracking correct Enter/Tab/Shift-Tab behavior across cursors became intractable (tab/shift-tab duplicated markers). Lesson: ship smart-list as single-cursor for M1; multi-cursor is a separate, hard milestone.　— _https://github.com/laurent22/joplin/pull/3581_
- swift-markdown SourceLocation is (line, UTF-8 column), 1-indexed — it does NOT give an absolute string offset, and NSTextView needs UTF-16 NSRange. Christian Tietze warns you must translate to a real String.UTF8View.Index / absolute offset yourself; naive line/column math breaks on multi-byte and astral characters. Off-by-one here corrupts byte-exact edits.　— _https://christiantietze.de/posts/2025/04/limits-of-swift-markdown-customization/_
- CodeMirror/Lezer's markdown parser has known quirks parsing nested lists (visible via .list.cmt-meta styling) — reinforcing architecture §4.2's rule that the incremental/highlight tree is NOT a semantic source of truth. Compute list structure from the full AST or a direct source scan, never from a highlight parse.　— _https://discuss.codemirror.net/t/nesting-ordered-and-bullet-lists-in-markdown-mode/3685_
- A recurring CodeMirror bold-toggle bug: inserting ** around a selection moved the selection to a 'mysterious area' because the anchor/head were not remapped through the change. Cursor placement must be recomputed via the ChangeSet (mapPos with the correct assoc side) so the caret lands INSIDE the markers, not outside.　— _https://discuss.codemirror.net/t/keymap-for-bold-text-in-lang-markdown/3150_

**要抄的做法（优秀实践）**
- Copy CodeMirror lang-markdown's insertNewlineContinueMarkup wholesale (as Swift): read the active markup context of the current line, and on Enter either reconstruct the marker for the innermost list/blockquote level or, if the item is EMPTY, delete that markup level to exit the list. This one function encodes continue + empty-exit correctly.　— _https://github.com/codemirror/lang-markdown/blob/main/src/commands.ts_
- Copy CodeMirror's renumberList policy: after continuing or indent/dedent, renumber only the CONTIGUOUS run where each item number equals prev+1 and STOP at the first gap — don't blindly rewrite the whole list. This matches user intent and avoids clobbering intentionally non-sequential lists.　— _https://github.com/codemirror/lang-markdown/blob/main/src/commands.ts_
- Copy CodeMirror's deleteMarkupBackward for Backspace at the end of a list/quote marker: first replace the marker with equivalent spaces (dedent one level), and only delete the spaces on a second Backspace. This gives the smooth 'unindent then remove' feel users expect.　— _https://github.com/codemirror/lang-markdown/blob/main/src/commands.ts_
- Copy the changeByRange + changes().mapPos(pos, assoc) pattern for toggle commands: build the edit, then remap anchor/head through the resulting ChangeSet with the correct association so multi-position selections and carets survive wrap/unwrap. In Swift, replicate by computing the new NSRange after applying the delta.　— _https://codemirror.net/examples/change/_
- Copy vscode-markdown (yzhang-gh, MIT) command surface and UX: toggleBold (⌘B), toggleItalic (⌘I), toggleStrikethrough, heading up/down as discrete commands, and word-expansion — when nothing is selected, toggling bold/italic operates on the whole word under the caret. Mature, battle-tested edge-case handling to mirror.　— _https://github.com/yzhang-gh/vscode-markdown/blob/master/src/formatting.ts_
- Follow MarkEdit's discipline: strictly GFM, no invented syntax, and formatting commands as pure text transforms delegated to a well-tested core. It keeps saves clean and predictable — the same restraint keeps Colophon byte-exact.　— _https://github.com/MarkEdit-app/MarkEdit_
- Follow Obsidian's model: 'Toggle checkbox status' is a first-class command bound to a hotkey (they deliberately freed ⌘Enter), and Enter-continuation / empty-item-exit is native editor behavior, not a plugin. Treat checkbox toggle and smart-list as core editor commands, not add-ons.　— _https://forum.obsidian.md/t/command-enter-to-checkoff-a-task-list-item-broken/42658/2_

- ListItem.checkbox (Checkbox?, off/on) and SourceLocation (line + UTF-8 column, 1-indexed; doc start = line1,col1) let us identify heading level, ordered-item index, and checkbox state from the full-AST track. But SourceLocation gives NO absolute offset — translate to String.UTF8View.Index / UTF-16 NSRange yourself before editing NSTextView. Immutable COW value types are thread-safe (safe to parse off-main per architecture §4).　（**swift-markdown (swiftlang)** · Active under swiftlang org (moved from apple); cmark-gfm-backed; develops on main. Already the chosen full-AST engine (architecture §4.2). · 许可: Apache-2.0 (matches Colophon) · https://github.com/swiftlang/swift-markdown）
- The undo-safe programmatic-edit recipe: guard shouldChangeText(in:replacementString:) → textStorage.replaceCharacters(in:with:) → didChangeText(); NSTextView then registers correct undo. insertText: is for USER typing only, not programmatic edits. Direct textStorage mutation bypasses undo. This is the bridge between L2's model edit and the on-screen view.　（**AppKit NSTextView shouldChangeText/didChangeText** · Current API, macOS 15/26. TextKit-2-safe: none of these read .layoutManager. · 许可: Apple SDK · https://developer.apple.com/documentation/appkit/nstextview/1449532-shouldchangetextinrange）

Essential for making each toggle/heading command its own crisp undo step.　（**AppKit NSTextView breakUndoCoalescing** · Current API, macOS 15/26. · 许可: Apple SDK · https://developer.apple.com/documentation/appkit/nstextview/1449384-breakundocoalescing）
- MarkEdit: native macOS Markdown editor, GFM-strict, CodeMirror-6-in-WebView. - vscode-markdown provides mature toggleBold/toggleItalic/toggleStrikethrough/heading commands with word-expansion when no selection is present — the clearest reference for the exact selection/caret rules of format toggles.　（**vscode-markdown (yzhang-gh)** · Widely used, maintained. Reference-only (TypeScript/VS Code). · 许可: MIT (Apache-2.0 compatible) · https://github.com/yzhang-gh/vscode-markdown/blob/master/src/formatting.ts）

**M1 建议.** For M1, implement all semantic + smart-list operations as pure Swift functions that take (source string, selection) and return (replacement edits, new selection), then funnel them through ONE model-layer method — call it applyTextEdit(range:replacement:newSelection:) on Document (L2). That method: (1) computes the byte-exact replacement (normalizing inserted "\n" to the document's recorded line-ending style, honoring the document's existing indent convention), (2) registers a single undo action on the Document's UndoManager with the inverse edit, (3) on MainActor pushes the change to the NSTextView via the shouldChangeText(in:replacementString:) → textStorage.replaceCharacters(in:with:) → didChangeText() bracket, calling breakUndoCoalescing() first so the command is isolated from typing coalescing, and (4) sets the selection. Do NOT let both NSTextView's built-in undo and the model register the same edit (double-undo). Port CodeMirror lang-markdown's three algorithms verbatim in spirit: insertNewlineContinueMarkup (Enter: continue marker, auto-number next ordered item, exit on empty item), deleteMarkupBackward (Backspace at end of marker deletes one markup level — replace-with-spaces then delete), and renumberList (renumber only the contiguous run where each item == prev+1, stop at a gap). Bold/italic = wrap/unwrap toggle with changeByRange-style per-range cursor remapping; when the selection is empty, expand to the surrounding word before toggling (copy vscode-markdown's UX) or insert empty **|** with the caret between markers. Heading up/down = rewrite the leading ATX run on each selected line, clamped to H1..H6, always keeping exactly one space after the hashes; handle the "no heading → add #" and "H1 up → paragraph" ends explicitly. Toggle checkbox = locate the ListItem.checkbox via the AST (or a `^\s*[-+*] \[([ xX])\]` scan of the line), flip only the single bracket character (space↔x), touching nothing else. Read block context synchronously from the source string (regex/line-scan), NOT from the debounced AST, because a command fired right after a keystroke may see a stale AST. Keep it single-cursor for M1. This keeps the AST-as-API seam (§7) intact — later the same edits can be re-expressed as StructuralEdit without touching the algorithms.

**待决（human call）**
- Ordered-list renumber policy: (a) auto-renumber to strict 1,2,3 after every edit, (b) CodeMirror-style renumber only the contiguous prev+1 run and stop at gaps, or (c) preserve users' lazy '1. 1. 1.' style and never renumber. Also: do we renumber on item DELETE, not just on continue/indent? Needs a product call — it changes bytes the user didn't type.
- Indentation unit for Tab-in-list and list continuation: spaces vs a real tab, and how many spaces (CommonMark aligns sub-items past the parent marker width). Must be byte-exact and ideally match the document's existing convention rather than a fixed constant. Also: does Tab indent everywhere or only inside lists (and insert plain indentation elsewhere)?
- Undo integration model (the architecture §5/§8 spike question this dimension depends on): does NSTextView keep its built-in undo with the model listening, or does the model fully own undo and NSTextView's is disabled? Semantic commands need this settled to avoid double-undo.
- Checkbox toggle details: emit lowercase 'x' or preserve existing case; and do we (Obsidian Tasks-style) append a done-date on completion? Recommend plain GFM 'x' with no date for M1 to stay byte-minimal — confirm.
- Whether M1 routes these through a lightweight text-edit primitive or already through the L2 StructuralEdit/AST seam (§7.2). Recommend the text primitive for speed, with a note to re-express later — needs sign-off that this doesn't prematurely bypass the seam.
- Heading up/down boundary behavior: does 'heading down' past H6 stop at H6 or wrap; does 'heading up' from H1 convert to a plain paragraph; and how to treat setext (===/---) headings if they appear (convert to ATX or leave alone).

**风险**
- Byte-exact violation via newline style: list continuation inserts '\n', but if the document is CRLF the inserted newline must be '\r\n'. Getting this wrong silently mixes line endings and breaks the byte-exact red line (architecture §3.2). Every inserted newline must be normalized to the document's recorded style.
- Byte-exact violation via whitespace normalization: indent/dedent and renumber must touch ONLY the intended characters and must not reflow or re-space other lines. A too-broad edit range corrupts untouched content.
- UTF-8(AST) ↔ UTF-16(NSRange) offset mismatch: swift-markdown SourceLocation is UTF-8 line/column; NSTextView uses UTF-16 NSRange. Emoji/astral characters make naive conversion off-by-one, editing the wrong bytes. Needs a tested offset-translation utility.
- Double undo: if both NSTextView's built-in undo and the L2 UndoManager register the same semantic edit, one Undo leaves the view and model out of sync. The single-choke-point + chosen undo model must prevent this.
- Undo coalescing: without breakUndoCoalescing(), a command fired mid-typing merges into the typing undo group, so Undo reverts both the format and the typed text — confusing. Must break coalescing around each command.
- Stale-AST race: the full AST is debounced/async (architecture §4.2); a command triggered immediately after a keystroke may read a stale tree and act on the wrong structure. Block context for commands must be derived synchronously from the source string, not the async AST.
- TextKit 2 traps: any code path that reads NSTextView.layoutManager to compute geometry/ranges silently downgrades to TextKit 1 (architecture §6.1). Also NSTextList is broken since macOS 14 — list indentation must be plain source spaces, never NSTextList/paragraph styles.
- Multi-cursor scope creep: attempting multi-cursor smart-list in M1 risks the exact intractability Joplin hit. Descoping to single-cursor is a risk-mitigation, but must be an explicit, documented M1 boundary.

## D6. Image paste and drag-to-disk, selected-paste URL auto-link (M1 MVP)

**执行摘要.** Both features are pure L2 source-string edits: pasting/dropping an image writes a file to a configurable folder and inserts the plain-text Markdown `![](relative/path)`; pasting a URL over a selection replaces it with `[selection](url)`. The single hard architectural constraint from Colophon's standards is that NEITHER feature may create an NSTextAttachment or touch NSTextView.layoutManager — the image lives on disk and only its Markdown reference enters the buffer, which keeps saves byte-exact and stays on TextKit 2. Writing into a subfolder of the already-open vault needs no extra sandbox prompt because security scope cascades to children; an attachment folder outside the vault would need its own bookmark, so MVP should keep attachments inside the vault. The mature designs to copy are Obsidian's built-in "default location for new attachments" + timestamp naming (`Pasted image YYYYMMDDHHMMSS.png`), Typora's per-document `typora-copy-images-to` front-matter override with a `./`-relative path and `${filename}` token, and VS Code's `markdown.copyFiles.destination` + Smart Paste. iA Writer's Content-Block model is a poorer fit (it uses a non-standard bare-path syntax and a managed Library, which conflicts with file-over-app and byte-exact CommonMark). The biggest sleeper risk is the WKWebView preview: R1.1/R1.3 restrict it to bundled resources with `img-src` locked down, so pasted local images will not render in preview until we add a custom `WKURLSchemeHandler` (or scoped read-access) — that is a preview-spike dependency, not a blocker for the editor feature itself.

**要避开的坑（前人教训）**
- Do NOT insert images as NSTextAttachment / rich-text glyphs. Christian Tietze's teardown shows Finder image drops into NSTextView yield file URLs and the naive path embeds an attachment cell — that is a rich-text representation that cannot round-trip to byte-exact Markdown and forces TextKit-1 attachment plumbing. For Colophon the image must stay on disk and only the plain `![](path)` text enters the source buffer.　— _https://christiantietze.de/posts/2021/11/nstextview-image-file-pasteboard/_
- Bridging NSURL to Swift URL during a drop silently discards the security-scoped/bookmark nature of the URL, turning it into a plain absolute path — subsequent scoped access can fail. Keep the NSURL as-is when you need the security scope.　— _https://christiantietze.de/posts/2021/11/nstextview-image-file-pasteboard/_
- Obsidian's built-in 'Attachment folder path' does NOT honor a bare relative name the way users expect — typing `images` dumps files in the vault root, not next to the note; true note-relative behavior required the community 'Custom Attachment Location' plugin with an explicit `./` prefix. Design the folder rule so 'relative to note' is a first-class, unambiguous option, not an accident of string parsing.　— _https://forum.obsidian.md/t/need-help-setting-up-a-relative-images-folder/61373_
- Typora's 'copy image to folder' has shipped path-resolution bugs (issue #4141: images copied to the wrong folder) and years of user confusion about absolute-vs-relative. The lesson: resolve the destination relative to the SAVED note's directory, require the note to be saved first, and unit-test the relative-path computation.　— _https://github.com/typora/typora-issues/issues/4141_
- Capturing the paste event yourself and also letting the editor's default run causes a double-paste; you must fully consume the event (preventDefault / return handled) when you take over. Applies directly to overriding paste/drop on NSTextView.　— _https://discuss.codemirror.net/t/customize-multicarret-copy-paste/3313_
- MarkEdit — the closest native-macOS plain-text peer (MIT) — deliberately does NOT write pasted images to disk (issue #1234: 'nothing happened' on Cmd-V of a photo); it stays plain-text and punts on attachments. Treat image-to-disk as a genuine differentiator to get right, not a solved commodity, and expect edge cases others avoided by not shipping it.　— _https://github.com/MarkEdit-app/MarkEdit/issues/1234_

**要抄的做法（优秀实践）**
- COPY Obsidian's naming and folder model: default attachment location choices (vault root | same folder as note | subfolder), plus deterministic collision-proof naming `Pasted image YYYYMMDDHHMMSS.png` for clipboard images (14-digit local timestamp). It is human-readable, sorts chronologically, and rarely collides; on the rare collision, append `-1`/`-2`.　— _https://forum.obsidian.md/t/how-to-have-pasted-file-automatically-renamed-with-timestamp-like-pasted-image-20240507222746-png/81475_
- COPY Typora's per-document override design for a later milestone: a front-matter key (`typora-copy-images-to: ./assets`) that beats the global setting, supports `./`/`../` relative paths and a `${filename}` token, plus a 'use relative path if possible' global toggle and an optional `./`-prefix compatibility switch. This is the cleanest plain-text-native way to make the folder rule per-note without a database.　— _https://support.typora.io/Images/_
- COPY VS Code's Smart Paste: `markdown.editor.filePaste.copyIntoWorkspace: mediaFiles` copies pasted media into the workspace and inserts a Markdown link, and `markdown.copyFiles.destination` maps globs to destination folders. This validates 'paste file -> copy into project -> insert relative link' as the expected modern default, and the glob-to-destination idea is a good V1 upgrade to a single global rule.　— _https://code.visualstudio.com/docs/languages/markdown_
- COPY the Obsidian paste-link plugin's URL-wrap edge-case handling: validate with the URL constructor (require a real scheme, so `https://x` and `file:///…` qualify but bare `example.com` does not); if the caret/selection is inside an existing link, paste normally; if an existing link is selected, replace only its URL; offer Shift-paste as force-plain.　— _https://github.com/jose-elias-alvarez/obsidian-paste-link_
- For drag-and-drop, customize pasteboard READING (Apple's guidance is to override `readSelectionFromPasteboard:type:` / handle the dragging pasteboard) rather than fighting `performDragOperation` internals, and restrict accepted types via `NSImage.imageTypes` so irrelevant drops don't highlight the view. Suppress the folder-drop 'copy or alias' dialog.　— _https://christiantietze.de/posts/2021/11/nstextview-image-file-pasteboard/_

**技术细节**
- Read clipboard/drop images with `pasteboard.readObjects(forClasses: [NSImage.self], options: nil) as? [NSImage]`, gated by `canReadObject(forClasses:options:)`; or pull raw bytes with `data(forType: .png)` / `.tiff`. Use `NSImage.imageTypes` to build the accepted-UTI set for drag filtering. Screenshots and most clipboard images arrive as PNG or TIFF; re-encode to PNG deterministically with `NSBitmapImageRep(data:).representation(using: .png, properties: [:])` so repeated pastes of the same image are byte-stable.　（**AppKit NSPasteboard / NSImage / NSBitmapImageRep** · Current, first-party; stable on macOS 15/26 SDK. · 许可: Apple SDK · https://developer.apple.com/documentation/appkit/nspasteboard/1524454-readobjects）
- For DROPPED files (Finder), the pasteboard yields `public.file-url` items, not file promises. Read them via `readObjects(forClasses: [NSURL.self])` with `.urlReadingContentsConformToTypes: NSImage.imageTypes`. COPY the source bytes verbatim (do not decode/re-encode) to preserve the user's exact image. Apps like Photos/Mail may instead offer file PROMISES — read `NSFilePromiseReceiver` and call `receivePromisedFiles(atDestination:options:operationQueue:reader:)`. MVP can support real file URLs first and add promise handling if needed.　（**NSDraggingInfo / NSFilePromiseReceiver** · Current, first-party. · 许可: Apple SDK · https://christiantietze.de/posts/2021/11/nstextview-image-file-pasteboard/）
- Sandbox: once the vault's security-scoped bookmark is resolved and `startAccessingSecurityScopedResource()` is active, writing into ANY subfolder of the vault is permitted — access cascades to the whole subtree (except MAC-protected system paths). So writing `<vault>/assets/Pasted image ….png` needs NO additional NSOpenPanel or bookmark. An attachment folder OUTSIDE the vault would require its own user-selected bookmark; avoid that in MVP. Construct child URLs by appending path components to the RESOLVED vault URL, and reuse the L5 atomic write (`Data.write(options: .atomic)`).　（**Security-scoped bookmarks / App Sandbox** · Current; behavior documented by Apple DTS. · 许可: Apple SDK · https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox）
- Relative-path computation: the Markdown destination must be the attachment path relative to the NOTE's directory (require the note to be saved on disk first). Use forward slashes. For paths containing spaces, either percent-encode (`Pasted%20image%20….png`) or use CommonMark angle-bracket destinations `![](<Pasted image ….png>)`. Verify the round-trip through swift-markdown so the derived AST link target matches the on-disk file. Unit-test this relative computation (Typora shipped bugs here).　（**CommonMark link destinations / swift-markdown** · swift-markdown is Apache-2.0, Apple-maintained, actively developed. · 许可: Apache-2.0 · https://support.typora.io/Images/）
- URL auto-link on paste: intercept paste in the NSTextView subclass (override `paste(_:)` or `readSelectionFromPasteboard`). If the pasteboard string trims to a single token that constructs a valid `URL` WITH a scheme, and the current selection length > 0, and the selection is not already inside/over a link node (check via the L2 structural range / AST), then replace the selection with `[<selection>](<url>)` as ONE undo-registered L2 edit. Otherwise call super. Provide a Shift-paste modifier (or a separate 'Paste as Plain Text' command) to bypass. Fully consume the event when you handle it to avoid double-paste.　（**NSTextView paste override + L2 edit intent** · Pattern validated across CodeMirror 6 and Obsidian; adapt to AppKit. · 许可: N/A (own code) · https://github.com/jose-elias-alvarez/obsidian-paste-link）
- TextKit 2 red line: to find the drop insertion index without touching `layoutManager`, use `NSTextView.characterIndexForInsertion(at:)` or the TextKit-2 path via `textLayoutManager`/`textLayoutFragment(for:)` — never read `.layoutManager`. The insertion itself goes through the L2 source-string edit intent, not `textStorage` attachment APIs, so no TextKit-1 downgrade and no attachment cell is created.　（**NSTextLayoutManager / NSTextView (TextKit 2)** · Current; layoutManager-read downgrade still present on macOS 26 per project docs. · 许可: Apple SDK · https://developer.apple.com/documentation/appkit/nstextview）

**M1 建议.** M1 should ship: (1) Image paste/drop that writes the file and inserts plain Markdown text via the L2 edit intent, never as an NSTextAttachment. Read the image from NSPasteboard/NSDraggingInfo with `readObjects(forClasses: [NSImage.self, NSURL.self])`; if the source is an existing file URL, COPY its bytes verbatim (no re-encode); if it is raw clipboard bitmap/screenshot data, encode deterministically to PNG via `NSBitmapImageRep`. (2) A configurable folder rule modeled on Obsidian: a global default ("same folder as note" | "vault root" | "subfolder relative to note, e.g. `assets`" | "fixed vault subfolder") with a per-document override read from `typora-copy-images-to`-style front matter deferred to post-MVP. Default to a note-relative `assets/` subfolder. (3) Naming = Obsidian-style `Pasted image YYYYMMDDHHMMSS.png` for clipboard images, original filename for dropped files; on collision append `-1`, `-2`, … after checking the destination directory. (4) Insert a CommonMark link whose destination is the path relative to the note's directory, with spaces either percent-encoded or wrapped in `<…>`. (5) URL auto-link: on paste, if the clipboard is a single valid absolute URL (validate by constructing a URL and requiring a scheme) AND the selection is non-empty AND the caret is not already inside a link, replace the selection with `[selection](url)`; otherwise fall through to normal paste. Provide Shift-paste as the force-plain escape hatch. The whole "write file + insert text" must be ONE undo group registered in L2 (per architecture §5); MVP undo removes only the inserted text and leaves the file (an orphan-attachment sweep is a later feature) — but document this. Keep attachments inside the vault so the existing security scope covers the write. Do all file I/O off the main thread via the L5 atomic-write path, then hop back to MainActor to apply the text intent.

**待决（human call）**
- Undo semantics for image paste: should undoing the text insertion also delete (to Trash) the written file, or leave it as an orphan? Obsidian/Typora leave orphans. Recommend MVP leaves the file and defers an 'unused attachments' sweep — but a human should confirm this is acceptable vs. registering file-trash in the same undo group.
- Default folder rule: note-relative `assets/` subfolder (recommended) vs. vault-root vs. same-folder-as-note. Pick the shipping default and the exact set of user-selectable options.
- Whether to re-encode ALL images to PNG for determinism, or preserve original bytes/format for dropped files and only encode raw clipboard bitmaps (recommended). Decide JPEG handling for large photos (Obsidian's Custom Attachment Location offers optional JPEG conversion).
- Filename scheme: adopt Obsidian's `Pasted image YYYYMMDDHHMMSS.png` verbatim, or use a content hash (dedupe-friendly, uglier), or keep original names for drops. Also decide whitespace policy (keep spaces, or replace with `-`).
- Preview rendering of local images: choose the mechanism to let the sandboxed, CSP-restricted WKWebView display vault-local images (custom `WKURLSchemeHandler` reading within the vault scope is the safest; alternative is scoped `img-src`/read-access). This is a preview-spike decision that gates whether pasted images are visible in preview.
- Per-document folder override via front matter (Typora's `typora-copy-images-to` model): ship in M1 or defer to V1? Recommend defer; ship a single global rule first.
- URL auto-link scope: only wrap when a scheme is present (strict), or also linkify bare `www.`/domain-like text? Recommend strict (scheme required) to avoid surprising the user.

**风险**
- Byte-exact violation risk: any code path that lets AppKit insert a dropped/pasted image as an NSTextAttachment (the DEFAULT NSTextView behavior) breaks byte-exact saving and drags the view toward TextKit-1 attachment handling. Must override paste/drop to intercept image data BEFORE AppKit's default rich-text insertion. This is the highest-severity risk and needs an explicit test.
- Preview blindness: R1.1/R1.3 lock the preview WebView to bundled resources with a strict `img-src`; without a scheme-handler, pasted images will show as broken in preview even though the file exists and the source is correct — a confusing UX regression that must be solved in the preview spike, not silently shipped.
- Relative-path bugs: computing the note-relative path wrong (Typora #4141) produces links that resolve on the author's machine but break for others or on export. Mitigate with unit tests over nested-folder cases and non-ASCII/space filenames.
- Security-scope loss on drop: bridging the dropped NSURL to Swift URL can strip the bookmark/scope; if the source needs scoped read (e.g., a file dragged from outside the vault), the copy can fail. Read bytes while the correct scope is held; for external sources, copy immediately during the drop handler.
- External/network paste: dragging or pasting an image referenced only by an http(s) URL (e.g., from a browser) — decide whether to download it (needs network entitlement, which R2.3 forbids in MVP) or just insert the remote URL as-is. MVP has no network entitlement, so remote-image download is out of scope; insert the URL link only.
- Undo/redo desync: if the file write and the text insertion are not bundled into a single L2 undo group, undo can leave the buffer and disk inconsistent (text removed but file lingering, or vice versa). Enforce one atomic undo group registered in the model layer.
- Concurrency: doing the disk write on the main thread will hiccup typing on large images; must write on a background queue (L5) and re-enter MainActor for the text intent, matching architecture §4.1.

## D7. Omnibar, full-text search, and command palette (search-index strategy for a 10k+ file folder library)

**执行摘要.** Colophon's M1 needs three distinct-but-related surfaces: (1) the omnibar "search = create" quick-switcher, (2) full-text search across a 10k+ file folder library, and (3) the command palette (Shift-Cmd-P). The central decision is the search-index strategy. My recommendation is a HYBRID, not a single index: a tiny in-memory title/filename/alias index that powers the omnibar and gives instant results the moment a Library opens (this is exactly how Obsidian's quick switcher and FSNotes stay fast at scale), PLUS a durable on-disk SQLite FTS5 index (via GRDB.swift) for content full-text search, kept incrementally in sync off the existing L5 FSEvents pipeline. The command palette is a THIRD, separate in-memory list of static commands, ranked by frecency with stable (not fuzzy-reshuffling) ordering — VS Code deliberately does not fuzzy-resort its command palette, and copying that avoids a known UX regression. I explicitly reject CoreSpotlight as the primary backend (sandbox/signing fragility, async donation latency, no ranking control, shared system index) and ripgrep-on-demand as the primary (per-keystroke rescan, sandbox subprocess friction) — though CoreSpotlight is worth adding later as an optional "let Finder/Spotlight find my .md" system-integration nicety, and an on-demand grep path is a fine fallback for regex/uncached queries. The single largest risk is CJK: the product is heavily Chinese-focused, and FTS5's default unicode61 tokenizer silently fails on Chinese (no word boundaries) — content search would return nothing for the core audience unless a custom bigram/per-character tokenizer is used. The search index is a DERIVED artifact (like the AST): it is never a source of truth, lives in the app container (never in the user's vault), and is fully rebuildable — which keeps it cleanly inside the settled six-layer architecture and byte-exact red lines.

## D8. FSEvents + NSFileCoordinator, no changed-on-disk dialog (external-change coordination + self-write dedup) for Colophon M1

**执行摘要.** Colophon's M1 goal (architecture §3.3, docs/19 M1) is: an external Agent edits a .md on disk and the editor reflects it instantly, with NO modal "file changed on disk" dialog. The industry-standard answer is a two-tier design: (1) NSFilePresenter + NSFileCoordinator for each *open* document (single-file coordination, iCloud/Dropbox-safe, and — critically — gives free self-write suppression), and (2) FSEvents watching the whole library folder (tree-scale sidebar/index freshness for non-open files). The crux the task names — self-write deduplication — has TWO layers because these two mechanisms differ: NSFileCoordinator can be told our presenter via initWithFilePresenter: and will then automatically suppress our own coordinated writes, but FSEvents knows nothing about file coordination, so at the FSEvents tier we must dedup ourselves. The robust, metadata-proof dedup is a CONTENT HASH sentinel (record SHA-256 of exactly the bytes we atomically wrote; on any event, re-read and compare — equal means our echo, ignore). mtime/inode comparison is unreliable specifically because our byte-exact spec mandates atomic temp+rename, and rename swaps the inode and updates ctime (not mtime), with mtime only 1s-resolution. The decision logic is exactly what architecture §3.3 already fixed: clean document → silent in-place reload; dirty document → non-modal Reload/Ignore/Compare affordance (never a blocking alert). MarkEdit gets the clean-case silent reload "for free" because it is NSDocument-based; Colophon deliberately is NOT NSDocument (architecture §2.1), so we must reimplement NSDocument's reload semantics — and CodeEdit's PR #2075 (MIT) is a near-perfect, legally-copyable reference for doing exactly that with a hand-rolled document.

**要避开的坑（前人教训）**
- MarkText (Electron, chokidar-based) fired a 'File Changed on Disk' conflict on EVERY save when the file lived in OneDrive/cloud sync — a textbook self-write dedup failure: the editor's own atomic write echoed back as an external change. This is precisely the loop Colophon must avoid; naive path/mtime watching without a content-hash guard reproduces it.　— _https://github.com/marktext/marktext/issues/1261_
- MarkText users had to file a feature request just to get any external-change handling and conflict options (reload vs keep) — showing that bolting this on late is painful. Colophon rightly makes it an M1 'door' (docs/19 M1), not an afterthought.　— _https://github.com/marktext/marktext/issues/2168_
- mtime comparison is 'considered harmful' for detecting your own write: an atomic rename (which byte-exact saving mandates) updates ctime, NOT mtime, and leaves the link count normal so the inode looks unchanged; mtime also has historically ~1s resolution. So mtime-equality can miss real changes AND fail to identify your own — content hashing is the only reliable discriminator.　— _https://apenwarr.ca/log/20181113_
- NSDocument in an iCloud Drive shared folder can intermittently reload OLDER data than last saved, and file-coordination TRUNCATES mtime milliseconds — so any modification-date comparison across a coordinated read is fragile. Reinforces hashing over mtime, and testing the iCloud path explicitly.　— _https://developer.apple.com/forums/thread/756264_
- BBEdit detects changes purely by time-last-modified, which breaks over NFS/SMB when server/client clocks are unsynced (users saw the auto-refresh preference do nothing). It also had a bug (fixed 12.6) where an external O_TRUNC-without-write left files unreloaded. Lessons: don't trust timestamps on network volumes, and handle the truncate-to-empty edge.　— _https://www.barebones.com/support/bbedit/notes-12.6.html_
- FSEvents can silently stop delivering events (errno=32 broken pipe writing to its internal pipe, observed macOS 15.7 Apple Silicon) — zero events despite the API 'working'. A watcher with no periodic reconciliation scan will strand a stale buffer. Always have a focus/foreground full-scan backstop.　— _https://pkg.go.dev/github.com/fsnotify/fsevents_
- Enabling kFSEventStreamCreateFlagFileEvents generates MANY more events and defeats the cheap directory-level temporal/spatial coalescing — a real cost for a vault that can hold 10k+ files (architecture §2.3 baseline). Keep directory-level events + app-side coalescing.　— _https://alexwlchan.net/2026/watch-files-on-macos/_
- Sandboxed apps have reportedly lost access to ~/Library/Mobile Documents (iCloud) mid-session around macOS 26.3; security-scoped bookmarks had a Sequoia-era regression fixed only in 15.1. **技术细节**
- FSEvents (FSEventStreamCreate / FSEventStreamSetDispatchQueue): C API for passively watching a whole directory tree with ONE stream. Flags: kFSEventStreamCreateFlagUseCFTypes | kFSEventStreamCreateFlagWatchRoot (detect root move/rename) | kFSEventStreamCreateFlagIgnoreSelf (drops events caused by THIS process — a useful cheap first-line self-write filter, but not sufficient alone since our writes may go via helper/coordination). latency ~0.05s; use the sinceWhen event-id for resume but treat its history DB as advisory and reconcile with a scan.　（**FSEvents (CoreServices)** · Fully supported on macOS 26 SDK / Xcode 26; C API, wrap in Swift. No deprecation. · 许可: Apple system framework · https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileCoordinators/FileCoordinators.html）
- NSFilePresenter + NSFileCoordinator: single-file coordination. Adopt NSFilePresenter (presentedItemURL, presentedItemOperationQueue, presentedItemDidChange(), presentedItemDidMove(to:), accommodatePresentedItemDeletion). Register addFilePresenter / removeFilePresenter. Reads: coordinate(readingItemAt:options:); writes: coordinate(writingItemAt:options:.forReplacing). Passing the presenter to NSFileCoordinator(filePresenter:) auto-excludes your own writes from your own presenter callbacks. Sandbox-compatible; the correct API for iCloud/Dropbox participation (architecture §3.3, §3.4).　（**NSFileCoordinator / NSFilePresenter (Foundation)** · Current and stable on macOS 26; standard Foundation. Watch the documented iCloud mtime-millisecond truncation quirk. · 许可: Apple system framework · https://developer.apple.com/documentation/foundation/nsfilepresenter）
- Self-write dedup via content hash: on each coordinated write, compute SHA256(bytesWritten) with CryptoKit (SHA256.hash(data:)) and store lastWrittenHash[path]. On any FSEvents/presenter event, coordinate-read the file, hash it, and if equal → own echo, ignore; if different → external change. Definitive because it ignores mtime/ctime/inode entirely (atomic rename makes those unreliable). Record the hash inside the write-coordination block to avoid a race with an external write landing in the same instant.　（**CryptoKit SHA256** · Current on macOS 26; trivial cost for typical Markdown file sizes. · 许可: Apple system framework · https://apenwarr.ca/log/20181113）
- CodeEdit PR #2075 'Reflect External File Changes': overrides presentedItemDidChange, compares modification date, checks isDocumentEdited, silently reloads when clean, defers to conflict UI when dirty, replaces contents WITHIN the text storage to preserve subscribers, registers a new undo frame on reload, clears the undo stack when no editors are open, and centralizes file loading. Directly transferable to Colophon's L2 Document + L5 Storage (which are not NSDocument but need the same semantics).　（**CodeEdit (reference implementation)** · Merged into CodeEditApp/CodeEdit; project actively maintained (2026). · 许可: MIT — safe to read AND adapt code · https://github.com/CodeEditApp/CodeEdit/pull/2075）
- MarkEdit: native macOS Markdown editor built on NSDocument + CodeMirror 6; therefore inherits NSDocument's clean-silent-reload / dirty-keep-and-warn behavior rather than hand-rolling it. - BBEdit: 'Automatically refresh documents as they change on disk' (Application prefs) + File → Reload from Disk, driven by time-last-modified. **M1 建议.** Build a two-tier watcher with a hash-based self-write guard, reimplementing NSDocument's clean/dirty reload semantics on Colophon's own Document (L2) + Storage (L5) layers.

TIER 1 — per open Document (single-file coordination):
- Make each open Document's coordinator object an NSFilePresenter (presentedItemURL + presentedItemOperationQueue = a dedicated serial queue). Register with NSFileCoordinator.addFilePresenter on open, removeFilePresenter on close.
- ALL our writes go through NSFileCoordinator(filePresenter: ourPresenter).coordinate(writingItemAt:options:.forReplacing) and inside that block do the atomic Data.write(.atomic) (architecture §3.1). Passing the presenter makes Foundation suppress presentedItemDidChange for our own write (Apple docs / Khanlou / mjtsai). IMPORTANT: create the coordinator on the SAME queue that receives presenter callbacks, or the suppression won't apply.
- ALL our reads (initial load AND reload) go through coordinate(readingItemAt:) so we play nice with iCloud placeholder download and other writers.
- On presentedItemDidChange, hop to a background read, coordinate-read the bytes, then decide (below). Do NOT block the presenter queue naively (CodeEdit's "block the calling thread" is subtle and deadlock-prone).

TIER 2 — whole-library FSEvents (for sidebar/search freshness of NON-open files, and as a backstop):
- One FSEventStreamCreate over the library root with kFSEventStreamCreateFlagWatchRoot | UseCFTypes, latency ~0.05s, started AFTER startAccessingSecurityScopedResource on the resolved bookmark URL and kept open for the watcher's life. Prefer directory-level events; do NOT enable kFSEventStreamCreateFlagFileEvents for a large vault (it defeats coalescing and floods events).
- Add your own per-path debounce/coalesce (≈100–200ms) on top of FSEvents latency to collapse the multi-event atomic write (temp create → rename → xattr) into one logical change.

SELF-WRITE DEDUP (the crux) — layered:
1. Cheap first filter: a short-lived "recently-wrote {path: expiry}" set to drop the immediate echo window.
2. Authoritative filter: keep lastWrittenHash[path] = SHA-256 (CryptoKit) of the exact bytes we wrote. On any confirmed event, re-read and hash; if equal to lastWrittenHash it's our own write → ignore. This sidesteps all mtime/ctime/inode ambiguity that atomic rename introduces. Record the hash inside the coordinated-write block so an external write that lands between our write and our record cannot be misclassified.

DECISION LOGIC (architecture §3.3, unchanged):
- Not dirty → SILENT reload: re-run strict-UTF8 decode + re-detect BOM/line-ending/trailing-newline (the agent may have changed them — never assume the old encoding), replace the CONTENTS inside the existing text storage (not the storage object, so TextKit2 layout + highlight subscribers survive), preserve caret/selection by offset, and register a new undo frame so the user can undo the external change (copy CodeEdit #2075). Never touch NSTextView.layoutManager during any of this (TextKit2 red line, engineering.md).
- Dirty → non-modal Reload / Ignore / Compare banner (inline, not a modal sheet that blocks typing). MVP ships Reload + Ignore fully; Compare can be a minimal whole-file diff view (per-hunk accept/reject is a documented V1 item, docs/19 §6.6).

RELIABILITY BACKSTOP: FSEvents can silently die (broken-pipe errno=32 seen on macOS 15.7). Run a lightweight reconciliation scan (compare on-disk mtime+size of open docs vs recorded) on app foreground / window focus, so a missed event never strands a stale buffer.

## D9. Focus mode (line/sentence/paragraph) and typewriter scrolling on a TextKit 2 NSTextView

**执行摘要.** Both features are pure presentation: they must never mutate the Markdown source string, so they are fully compatible with the byte-exact red line — focus mode changes on-screen color, typewriter mode changes scroll offset, neither touches bytes. On TextKit 2 there are exactly two hard problems. (1) Dimming non-focused text the "correct" way — NSTextLayoutManager rendering attributes (addRenderingAttribute/setRenderingAttributes on foregroundColor) — hits a documented, still-open framework bug (FB9692714): after invalidateLayout the view often does not redraw, confirmed by an Apple DTS engineer to occur even outside SwiftUI on macOS 26. (2) Typewriter centering needs an accurate caret rectangle, but TextKit 2 layout-fragment frames are approximate until ensureLayout runs, and full-document ensureLayout takes seconds on large files. Both are solvable — dimming via a local-range invalidation + forced viewport relayout (with a translucent scrim-overlay as a reliable fallback), and typewriter via top/bottom textContainerInset overscroll plus a manual NSClipView scroll that centers the caret rect computed from a small local ensureLayout. The focus-range math is cheap: line = NSString.paragraphRange/line fragment; sentence = NaturalLanguage NLTokenizer(unit:.sentence); paragraph = NSString.paragraphRange (swift-markdown SourceRange only if you want to focus a whole block like a fenced code block or list). The dominant risk is the rendering-attribute redraw bug; it warrants a short spike on macOS 15 and 26 before committing dimming to M1, and it is the reason to consider shipping typewriter scrolling in M1 and deferring dimming polish. iA Writer's own guidance — Focus centering fights you during revision, so it must default OFF with a frictionless exit — is a settled design constraint (design-direction §4.4) and matches the engineering reality.

**要避开的坑（前人教训）**
- iA Writer's own docs warn that Focus Mode's vertical centering conflicts with the area you select to edit, causing the screen to jump vertically during revision — so it is meant for the drafting phase and should be toggled OFF when editing. This is why Colophon defaults focus/typewriter OFF with a frictionless exit (already captured in design-direction §4.4).　— _https://ia.net/writer/support/editor/focus-mode_
- The Apple DTS engineer confirmed that NSTextLayoutManager addRenderingAttribute + invalidateLayout does NOT reliably redraw the NSTextView — even without SwiftUI, on macOS 26. STTextView's maintainer filed FB9692714 for exactly this. Do not assume the naive 'set attribute, invalidate' loop will refresh; budget for a forced-relayout workaround or an overlay fallback.　— _https://developer.apple.com/forums/thread/817471_
- Apple states TextKit 2 layout-fragment frames are intentionally approximate until ensureLayout(for:) covers them, and full-document ensureLayout can take seconds — whereas NSTextView scrolls to document end in milliseconds. Naive typewriter centering that reads fragment frames before layout lands in the wrong spot or forces a slow full-doc layout.　— _https://developer.apple.com/forums/thread/761364_
- The deathau Obsidian typewriter plugin had an 'unexpected line jumping' bug (Issue #6) and had to restrict scrolling to keyboard arrows and typing edits, explicitly NOT mouse selection, to stop the fight with the user. - Copy iA Writer's three-grain model exactly: Sentence, Paragraph, and Typewriter — and make Typewriter scrolling independently toggleable from the dimming grains (a user can want centered scrolling without dimming, or vice versa).　— _https://ia.net/writer/support/editor/focus-mode_

**技术细节**
- NSTextLayoutManager rendering attributes (setRenderingAttributes(_:for:) / addRenderingAttribute(_:value:for:)) are the TextKit-2-pure, non-destructive way to recolor/dim text without mutating the attributed string or the source bytes — the correct primitive for focus dimming. Set a base dimmed foregroundColor over the whole range and full ink over the focus range.　（**NSTextLayoutManager (AppKit/TextKit 2)** · Shipping macOS 11+; still has open redraw bug FB9692714 on macOS 26. · 许可: Apple system framework · https://developer.apple.com/documentation/uikit/nstextlayoutmanager）
- FB9692714: rendering attributes do not reliably draw after invalidateLayout. - Sentence focus: NLTokenizer(unit: .sentence) — call setLanguage before setting .string, then enumerateTokens over ONLY a window around the caret (e.g., the current NSString paragraph, not the whole document, to stay cheap on large files); find the range containing the caret String.Index. Handle caret-at-upperBound (boundary) and the nil case when the caret sits in inter-sentence whitespace. ## D10. Autosave and filesystem version history

**执行摘要.** M1 should ship (1) autosave = debounce-on-idle + save-on-blur/resign-active + save-on-close, where every write is byte-exact and atomic; and (2) a local snapshot version store living in the app container, modeled on VS Code "Local History" and Obsidian "File recovery" (per-file folder + JSON manifest + full-content blobs), NOT an embedded Git repo. Two research findings drive the snapshot-vs-Git call. First, the macOS-native Versions API (NSFileVersion, what iA Writer surfaces as File > Revert To) is coupled to on-disk file identity and NSFileCoordinator; our mandated byte-exact atomic replace changes file identity and orphans versions, and replaceItemAt sporadically fails (Cocoa 513) on iCloud/Dropbox — so we cannot lean on system Versions as our primary store. Second, embedded Git (FSNotes' approach) pulls in libgit2 (GPLv2-with-linking-exception, which brushes our "no GPL" red line), a sporadically maintained Swift wrapper, cannot live inside an iCloud folder, and is heavier than needed. A self-owned snapshot directory is the most controllable, byte-exact-friendly path and it directly seeds Route B's "snapshot before every AI write" checkpoint rollback. Delete goes through FileManager.trashItem — never unlink.

**要避开的坑（前人教训）**
- Boostnote stored notes as proprietary .cson (not .md) and later pivoted to a SaaS that shut down 2025-09-30; users lost portability and trust. Version history must never introduce a proprietary at-rest format for the user's actual files — snapshots live beside/outside the .md files, the .md stays pure.　— _docs/03-windows-legacy.md (Boostnote entry)_
- Laverna died specifically because its maintainer could not make sync/multi-device reliable and users lost notes; the wiki now says 'LAVERNA IS A DEAD PROJECT'. Do not build sync or a versioning scheme that depends on our own sync — keep versions as local files and let iCloud/Git handle sync.　— _docs/03-windows-legacy.md (Laverna entry)_
- iA Writer outsources version history entirely to iCloud Drive / NSFileVersion (File > Revert To > Browse All Versions); if the user is NOT on iCloud, version history is effectively absent and recovery falls back to the provider's web trash. Relying solely on the system Versions store leaves non-iCloud users unprotected — our own store must work regardless of storage provider.　— _https://ia.net/writer/support/help/version-history_
- NSFileVersion (the macOS Versions store iA Writer uses) is bound to on-disk file identity and must be manipulated under NSFileCoordinator; a plain atomic replace (replaceItemAt / Data.write .atomic) changes file identity and can orphan/lose the tracked versions. Our byte-exact atomic-replace requirement is fundamentally in tension with treating system Versions as the primary store.　— _https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/LowLevelFileMgmt/Articles/FileManagement.html_
- FileManager.replaceItemAt sporadically fails with NSCocoaErrorDomain 513 ('You don't have permission to save the file') specifically on iCloud Drive and Dropbox items. The atomic-replace path needs a retry + coordinated-in-place fallback, or autosave will intermittently fail on exactly the cloud folders our users keep vaults in.　— _https://developer.apple.com/forums/thread/817068_
- Obsidian's File Recovery keys snapshots by the note's ABSOLUTE path, so moving the vault breaks recovery ('you may need to move it back'). Key our snapshot store by a stable file ID / security-scoped bookmark and update it on FSEvents renames, not by absolute path.　— _https://obsidian.md/help/plugins/file-recovery_
- VS Code Local History only records versions for files edited INSIDE VS Code — external edits are invisible to it. Since our product explicitly must reflect external/agent edits (architecture.md 3.3), the snapshot store should also capture content seen via FSEvents/reload, not only our own saves, or agent-made changes won't be recoverable.　— _https://code.visualstudio.com/updates/v1_66_
- Cloning whole directory hierarchies with clonefile(2) is 'strongly discouraged' and can crash the kernel; use copyfile/FileManager.copyItem instead. Do not hand-roll clonefile on folders for snapshot storage.　— _https://developer.apple.com/forums/thread/784446_
- Mark Text/Muya and other predecessors earned lasting reputational damage from data-loss bugs; the repo's own red line is 'data loss = reputation death.' Autosave must never trade correctness (byte-exact + atomic) for convenience, and the version store is the safety net for when a save path has a bug.　— _docs/03-windows-legacy.md (Mark Text entry); planning/standards/architecture.md 3_

**要抄的做法（优秀实践）**
- Copy VS Code 'Local History': per-file hashed subfolder under Application Support containing an entries.json manifest (source path, timestamps, snapshot filenames) plus full-content snapshot blobs. Simple, greppable, no DB, survives app crashes. Store OUTSIDE the user's vault so vault-level loss doesn't take the history with it.　— _https://bobbyhadz.com/blog/view-vscode-local-history_
- Copy Obsidian 'File recovery' cadence: only snapshot when content actually changed, enforce a minimum interval between snapshots (default 5 min), keep for a bounded window (default 7 days), prune automatically, and let the user configure interval + retention. It's enabled by default because 'it's too late to enable when you've already lost data.'　— _https://obsidian.md/help/plugins/file-recovery_
- Copy FSNotes' storage placement: keep the version store OUT of the iCloud Drive folder (iCloud does not sync .git / snapshot stores well) — FSNotes defaults its Git repos to ~/Library/Containers/.../Application Support/Repositories, allowing any path except iCloud Drive. Our app-container History dir satisfies this automatically.　— _https://github.com/glushchenko/fsnotes/wiki/Backup-&-Versioning-of-Notes_
- Copy iA Writer's restore UX: a File > Revert To flow with 'Last Opened / Previous Save' quick options plus a 'Browse All Versions' timeline where the user scrubs a dated list and clicks Restore. Pair with trash-based deleted-file recovery (right-click > Move to Trash, recover from Finder Trash).　— _https://ia.net/writer/support/help/versions-and-backups_
- Use FileManager.replaceItemAt(_:withItemAt:) rather than raw Data.write(.atomic) for the atomic swap: it performs a save/replace-intent exchange that carries over the original's permissions, ownership and (most) extended attributes, whereas a blank overwrite starts fresh and can drop metadata.　— _https://eclecticlight.co/2025/12/17/which-extended-attributes-does-macos-tahoe-preserve/_
- Lean on APFS copy-on-write for near-zero-cost snapshots: FileManager.copyItem on the same APFS volume automatically produces a clonefile (shares data extents, diverges lazily on write), so retaining many snapshots of large files costs almost nothing until they diverge. Confirmed by Apple engineers that copyItem is built on copyfile/clonefile.　— _https://eclecticlight.co/2020/04/14/copy-move-and-clone-files-in-apfs-a-primer/_

**技术细节**
- Atomic byte-exact replace: write temp file in the destination's directory, then FileManager.replaceItemAt(dest, withItemAt: temp, backupItemName:nil, options:[]) inside NSFileCoordinator.coordinate(writingItemAt: dest, options: .forReplacing). Preserves permissions/ownership/xattrs. Must handle sporadic Cocoa error 513 on iCloud/Dropbox with retry + coordinated in-place fallback.　（**Foundation FileManager.replaceItemAt / NSFileCoordinator** · Current, macOS 15/26 SDK; documented 513-on-cloud failure mode as of 2025 · 许可: Apple SDK (system) · https://developer.apple.com/forums/thread/817068）
- Extended-attribute preservation nuance: macOS classifies file ops by 'intent'; a 'safe save' (atomic replace) strips xattrs flagged C (XATTR_FLAG_CONTENT_DEPENDENT, e.g. encoding/position/checksums) that a plain copy would keep, and never preserves N-flagged ones. If any user/agent xattr must survive a content change, read it pre-write via getxattr/listxattr and re-apply via setxattr after replace.　（**getxattr/setxattr/listxattr (sys/xattr.h)** · Current; behavior reconfirmed for macOS Tahoe (26) Dec 2025 · 许可: Apple SDK (system) · https://eclecticlight.co/2025/12/17/which-extended-attributes-does-macos-tahoe-preserve/）
- Trash-on-delete: FileManager.default.trashItem(at: url, resultingItemURL: &out); in sandbox, resolve the security-scoped bookmark, call startAccessingSecurityScopedResource() before and stopAccessingSecurityScopedResource() (defer) after. Known quirks: Trash icon may not refresh on some USB/APFS volumes; group-container .Trash relocation can make listing Trash return empty.　（**Foundation FileManager.trashItem** · Current, stable API; minor UI-refresh bugs noted 2025 · 许可: Apple SDK (system) · https://developer.apple.com/documentation/foundation/filemanager/1414306-trashitem）
- System Versions (what iA Writer surfaces) without NSDocument: NSFileVersion.addVersionOfItem(at:withContentsOf:options:) creates a version manually; enumerate via otherVersionsOfItem(at:)/currentVersionOfItem(at:); restore via replaceItem(at:options:) using .byMoving under coordinated writes. APFS stores versions block-level (copy-on-write) in per-volume .DocumentRevisions-V100. Fragile with our atomic-replace identity changes — evaluate as a SECONDARY/optional bridge only.　（**Foundation NSFileVersion** · Current; must be used under NSFileCoordinator; identity-coupling caveats · 许可: Apple SDK (system) · https://developer.apple.com/documentation/foundation/nsfileversion）
- APFS clonefile(2): instant copy-on-write clone sharing data extents; new inode with its own attributes/xattrs/ACLs; diverges lazily on write. Reached automatically via FileManager.copyItem when src+dst are on the same APFS volume (both built on copyfile). Direct clonefile on DIRECTORIES is 'strongly discouraged' (kernel-crash risk) — use copyItem for hierarchies. No retroactive dedup API exists.　（**clonefile(2) / FileManager.copyItem** · Current since macOS 10.12; folder-clone caveat reconfirmed 2026 · 许可: Apple SDK (system) · https://developer.apple.com/forums/thread/784446）
- Embedded-Git option (FSNotes' approach, added FSNotes 3.7.0): libgit2 is the C engine; Swift bindings SwiftGit2 (MIT wrapper). libgit2 itself is GPLv2 WITH a linking exception — legally linkable from Apache-2.0 code, but it grazes the project's 'no GPL/AGPL' red line and needs an explicit human call. SwiftGit2 shows commits into late-2025 but is historically low-activity and still ships fat binaries (not XCFramework); alternatives SwiftGitX and swift-libgit2 exist. Git repos must be kept out of iCloud folders and pruned via gc.auto/git gc (text delta-compresses well; watch loose-object accumulation from many small commits).　（**libgit2 + SwiftGit2 (or SwiftGitX / swift-libgit2)** · libgit2 maintained; SwiftGit2 sporadically maintained (updated Nov 2025, fat-binary tech debt) · 许可: libgit2: GPLv2+linking-exception (FLAG); SwiftGit2 wrapper: MIT · https://github.com/SwiftGit2/SwiftGit2）
- Snapshot-store layout to copy: <AppSupport>/Colophon/History/<fileKey>/entries.json (manifest: id, sourcePath, timestamp, contentHash, size, origin) + hashed full-content blob files. Dedup snapshots by contentHash; prune by time window and/or keep-N. Manifest is an internal, versioned format (VS Code's entries.json has no public API and is fragile if parsed externally — treat ours as private and stable).　（**Custom (Foundation FileManager + JSONEncoder)** · Design pattern proven in VS Code (1.66+, 2022) and Obsidian File Recovery · 许可: N/A (own code) · https://code.visualstudio.com/updates/v1_66）

**M1 建议.** For M1, build a self-owned "Local History" snapshot store in the app container (Application Support), not an embedded Git repo and not the system NSFileVersion store. Concrete design: (A) Autosave: on text change start a ~1-2s idle debounce timer; also flush immediately on window/blur (resignFirstResponder), app resignActive/deactivate, and document close; never autosave mid-composition (guard IME marked text). Each flush writes byte-exact per architecture.md 3.1-3.2. (B) Atomic write: write the exact source string (preserving BOM, LF/CRLF, trailing-newline) to a temp file in the SAME directory, then FileManager.replaceItemAt(dest, withItemAt: temp) wrapped in NSFileCoordinator.coordinate(writingItemAt:options:.forReplacing) — replaceItemAt preserves permissions/ownership/xattrs better than Data.write(.atomic). Handle the known Cocoa-513 sporadic failure on iCloud/Dropbox with a bounded retry, then fall back to a coordinated in-place write; re-apply any critical xattrs you read pre-write (safe-save intent strips C-flagged content-dependent xattrs). Suppress the resulting FSEvents self-trigger (architecture.md 3.3). (C) Snapshot store layout (copy VS Code): <container>/Application Support/Colophon/History/<fileKey>/entries.json + hashed full-content blobs; entries.json records {snapshotID, sourcePath, timestamp, contentHash, lineEnding, size, origin: user|autosave|preWrite}. Key <fileKey> off the file's security-scoped bookmark / a stable ID, NOT the absolute path — Obsidian keys by absolute path and breaks when the vault moves; track renames via FSEvents and update the mapping. (D) Snapshot triggers: take a pre-write snapshot of the OLD content immediately before every save (this is the Route B checkpoint seed), plus a debounced on-change snapshot; dedup by contentHash so no-op saves don't grow the store; enforce a minimum inter-snapshot interval (Obsidian uses 5 min). (E) Retention/pruning: time window (default ~7 days like Obsidian) OR keep-last-N per file, whichever the user picks, plus an optional total-size cap; prune on app launch and after each snapshot. (F) Restore-one-file UI (copy iA Writer File > Revert To): a per-document timeline/list of snapshots with a diff preview against current; Restore first snapshots the current buffer (so restore is itself undoable), then loads the chosen version into the L2 Document via the model-layer undo entry point. (G) Delete: FileManager.trashItem(at:resultingItemURL:) with the security-scoped resource started; never unlink. Storage cost is near-zero if you clone via FileManager.copyItem on the same APFS volume (copy-on-write), but since the byte-exact source is already in memory you can just write blobs directly. Defer embedded Git and NSFileVersion integration; keep the snapshot store's manifest format versioned so a future Git or system-Versions bridge can be added without migration pain.

**待决（human call）**

**风险**
- Storage growth: full-content snapshots of large/frequently-edited files accumulate (Obsidian warns to monitor usage). Mitigate with contentHash dedup, APFS clone-backed blobs, min-interval, and enforced retention/size cap — but a runaway store on a small SSD is a real support risk.
- Atomic-replace on cloud folders (iCloud/Dropbox) intermittently fails with Cocoa 513; without a robust retry + fallback, autosave silently fails on exactly the folders users keep vaults in — the highest-severity data-safety risk.
- Absolute-path keying (Obsidian's mistake) silently loses history when a file/folder is moved or renamed; requires FSEvents-driven rename tracking and a stable file identifier, which adds complexity and its own edge cases.
- App-container snapshots are NOT a real backup: deleting the app/container, or a full-disk failure, takes the history with it. Must communicate clearly ('this is local recovery, not backup — use iCloud/Time Machine') to avoid false confidence.
- Atomic replace strips content-dependent (C-flagged) xattrs by save-intent; if a user or agent relies on such an xattr on a .md file, it is lost on every save unless explicitly preserved — a subtle byte-adjacent data-loss vector distinct from the in-file byte-exact guarantee.
- NSFileVersion/system-Versions coupling to file identity means any future attempt to also feed the system store will be fragile under our atomic-replace pipeline; building on it prematurely could waste effort or create inconsistent version timelines.
- FSEvents self-trigger: our own snapshot writes and atomic saves generate FSEvents; without solid self-write suppression (architecture.md 3.3) the store could snapshot its own writes or loop.
- Embedded-Git path (if ever chosen) carries maintenance risk: SwiftGit2 is sporadically maintained with fat-binary tech debt, libgit2 cannot live in iCloud folders, and many small commits accumulate loose objects requiring periodic gc — added surface area for a solo maintainer.

## D11. Two calibrated themes, macOS conformance, Liquid Glass, fonts

**执行摘要.** The repo has already settled the hard calls I should build on, not re-open: terracotta #B23A28 as a scarce "rubric" accent confined to the caret + cursor-line markers (never chrome, never headings); warm paper canvas (#FBFAF6 light / #F4EDDD paper / #1C1B19 dark) with warm-near-black ink, never pure black/white; three type roles (SF Pro chrome / duospace editor / New York preview); chrome uses system semantic colors + SF Symbols + standard components; editor content is never glass; byte-exact and the TextKit-2 layoutManager red line are inviolable. My research confirms all of these are technically sound for M1 and maps them to concrete APIs.

Key results: (1) Fonts — iA Writer Duo/Duospace/Mono and IBM Plex Mono are both SIL OFL 1.1, which explicitly permits bundling inside an Apache-2.0 app (don't sell the font alone, ship the OFL text + copyright, rename if modified). New York is the opposite: it is a system font that MUST NOT be bundled — reach it via the CSS `ui-serif` generic family in the WKWebView preview and via `NSFontDescriptor.withDesign(.serif)` in AppKit, never ship .otf files. (2) Themes — implement tokens as an Asset Catalog color set with explicit light/dark variants (dynamic NSColor), plus a MarkEdit/CodeMirror-shaped token object (background, foreground, caret, selection, lineHighlight, gutter, + syntax-tag colors) so the editor theme and preview CSS share one schema, exactly as ui-and-design §5.2 already mandates. (3) Contrast — #B23A28 on white is ~5.9:1 (passes WCAG AA, fails AAA normal text); safe for a caret/marker accent, and markers also carry shape so color is never the sole signal. (4) Liquid Glass — recompiling with Xcode 26 gives NavigationSplitView sidebar + toolbar automatic glass for free; any explicit `glassEffect`/`GlassEffectContainer`/`.buttonStyle(.glass)` must sit behind `if #available(macOS 26, *)` with a macOS 15 fallback and self-downgrade under Reduce Transparency.

The single biggest technical risk to the signature feature: TextKit-2 `NSTextLayoutManager` rendering-attributes for the cursor-line rubric highlight are reported unreliable under NSViewRepresentable (highlight fails to appear/update). This needs an M1 spike before committing the rubric system's visual mechanism.

**要避开的坑（前人教训）**
- Zed's Markdown preview renders H1/H2/H3 at nearly identical sizes, making heading hierarchy invisible and un-customizable — the named cautionary example in the repo's own docs/12. M1's preview must make the H1→H6 size ladder unmistakable at a glance; do not let optical-size/CSS collapse the steps.　— _docs/12-ui-design-patterns.md (§五-B-9); design-direction.md §3.4_
- Classic AppKit dark-mode bug: caching a CGColor extracted from an NSColor (e.g. on a layer) freezes it — it will not switch to the dark variant when appearance flips. Store the NSColor and resolve at draw time; drop caches in viewDidChangeEffectiveAppearance.　— _https://mackuba.eu/2018/07/10/dark-side-mac-2/_
- When drawing NSAttributedStrings whose attribute set lacks foregroundColor, AppKit defaults to BLACK for backward compatibility — so syntax-colored text can render black-on-dark. Always set an explicit dynamic foregroundColor (e.g. .labelColor or a token color) on every run.　— _https://indiestack.com/2018/10/supporting-dark-mode-adapting-colors/_
- Applying style/attribute changes inside NSTextStorage.processEditing() or NSTextStorageDelegate methods moves the text view's caret. Christian Tietze documents the fix: recolor from NSText.didChangeNotification / NSTextViewDelegate.textDidChange instead. Directly relevant to the rubric marker recoloring.　— _https://christiantietze.de/posts/2017/11/syntax-highlight-nstextstorage-insertion-point-change/_
- A developer reported that TextKit-2 NSTextLayoutManager rendering-attributes for dynamic sub-range highlighting are unreliable inside an NSViewRepresentable: the highlight often never appears, or appears once and stops updating as the range changes. This is exactly the mechanism the cursor-line 'rubric' highlight would use — spike it before committing.　— _https://developer.apple.com/forums/thread/114433_
- Apple's New York font is licensed only for developing/mocking up software on Apple platforms and does NOT appear in font enumerations — you cannot self-host or bundle the .otf. Anyone who ships the file risks a license violation. Reach it via ui-serif (web) / withDesign(.serif) (AppKit) instead.　— _https://furbo.org/2018/03/28/system-fonts-in-css/_
- Bridging an AppKit toolbar with SwiftUI glass without setting hidesSharedBackground=true stacks two glass surfaces (the 'glass-on-glass' artifact Apple's HIG explicitly warns against). Set hidesSharedBackground at the bridge.　— _https://developer.apple.com/videos/play/wwdc2025/323/_
- MWeb shipped 32 themes and it bought no reputation for polish (repo's own reference). Chasing theme count is a trap; M1 should ship two themes that survive pixel review in both appearances rather than many mediocre ones.　— _docs/12-ui-design-patterns.md (§三, §六-3)_
- iA explicitly asks that users of their OFL fonts not clone iA Writer's product/brand ('don't be a copycat'). Using iA Writer Duospace is legally fine under OFL, but the visual identity must be our own rubric system, not a recolored iA Writer.　— _https://github.com/iaolo/iA-Fonts_

**要抄的做法（优秀实践）**
- Copy MarkEdit's theming shape: light and dark objects, each carrying a colors record (background, foreground, caret, selection, lineHighlight, gutter) plus syntax-tag→color mappings. 1. **风险**
- Signature-feature risk: the cursor-line rubric highlight depends on TextKit-2 rendering attributes that are reported unreliable under NSViewRepresentable. If the spike fails, the visual mechanism must change (per-run coloring of the current line) — schedule this spike early in M1 before the rubric system is locked.
- Warm custom selection wash (accent@12–15%) in the editor departs from the system selection color; must verify it reads clearly over both canvases, doesn't fight the terracotta caret, and remains legible under VoiceOver/high-contrast. - Terracotta sits near the universal red=error/delete UI semantic; confining it strictly to caret + structural markers + a single checkbox flash (never chrome, never headings) is the mitigation and must be enforced in review, or the accent will read as 'error'.

- New York via ui-serif may not reliably engage the variable optical-size axis in WKWebView; heading sizes may need explicit font-size steps and font-optical-sizing rather than relying on the axis — verify rendered output, don't assume.
- Dark-mode color correctness is easy to get subtly wrong (cached CGColor, unset foregroundColor→black, stale caches on appearance flip); without disciplined dynamic-color usage the dark theme will show black-on-dark text or non-adapting accents.

## D12. HTML/PDF export, release automation (sign→notarize→appcast→Release), Sparkle auto-update, Homebrew cask

**执行摘要.** M1's export and shipping path can be built almost entirely on Apple frameworks plus three well-maintained MIT/permissive tools (create-dmg 8.1.0, Sparkle 2.8+, Homebrew livecheck :sparkle), so nothing here threatens the byte-exact/TextKit-2/Apache-2.0 red lines — export is a strictly one-way Model→HTML→PDF path in L4, never touching the editor's TextKit stack. The single most important export decision is to NOT use WKWebView.createPDF() as the primary path: it renders the whole document onto one giant non-paginated page and has burned many developers. Use WKWebView.printOperation(with:) (which drives NSPrintOperation and paginates correctly) with NSPrintInfo.jobDisposition = .save, remembering the two non-obvious gotchas that cause blank/crashing output: you MUST set printOp.view.frame before running, and you MUST call runOperationModalForWindow (not runOperation). For self-contained HTML export, render the preview in an offscreen WKWebView and grab document.documentElement.outerHTML after Mermaid/KaTeX finish, so the exported file is static, offline, and byte-for-byte the same styling as the preview. The shipping path is a mature, well-trodden GitHub Actions recipe: sign .app → staple → create-dmg → sign+notarize+staple DMG → sign DMG with Sparkle sign_update / generate_appcast (EdDSA) → publish appcast + DMG. The deferred M0 Sparkle plan (planning/M0/sparkle-setup.md) is sound and current; build directly on it. Homebrew ships as a self tap (colophon-app/tap) with a :sparkle livecheck and the now-mandatory auto_updates true stanza.

**要避开的坑（前人教训）**
- Markdown Preview Enhanced's PDF/PNG export routes through Puppeteer/headless Chrome; Chromium-detection failures are its single highest-frequency bug and long documents take minutes to export. Colophon's native WebKit/PDFKit path is explicitly the fix — do not reintroduce a headless browser.　— _docs/07-ide-terminal.md (Markdown Preview Enhanced 不足)_
- MPE's exported PDFs lack bookmarks/outline (TOC) — a persistent user complaint. Add a PDFKit outline from the heading tree so Colophon's PDF isn't the same disappointment.　— _https://github.com/shd101wyy/vscode-markdown-preview-enhanced_
- WKWebView.createPDF(configuration:) does NOT paginate — every capture contains the entire document on one page regardless of frame. Multiple developers wasted effort splitting frames before discovering this. Use printOperation(with:) instead.　— _https://developer.apple.com/forums/thread/700418_

**M1 建议.** Build export as a self-contained L4 subsystem with a single reusable "export HTML" that the preview, HTML export, and PDF export all share (Model→HTML, one way).

PDF (primary path): Load the export HTML into a dedicated offscreen WKWebView; wait for didFinish AND for Mermaid/KaTeX render completion (a JS-side promise/flag polled via evaluateJavaScript). Then: let op = webView.printOperation(with: printInfo); set printInfo.jobDisposition = .save and printInfo.dictionary()[.jobSavingURL] = fileURL; set op.view!.frame = webView.bounds; set op.showsPrintPanel = false / op.showsProgressPanel = false; call op.runModal(for: window, ...) i.e. runOperationModalForWindow (NOT runOperation — that yields blank PDFs). Ship a print stylesheet (@media print + @page { size: A4/Letter; margin: … }) so pagination and margins are controllable. Do NOT rely on WKWebView.createPDF() for multi-page docs. Optionally post-process with PDFKit (PDFDocument) to inject a bookmark/outline from the heading tree — this is the exact gap users complain about in Markdown Preview Enhanced's PDF output, and PDFKit makes it cheap. Skip custom page headers/footers for M1 (no reliable WebKit API; CSS @page margin-boxes are buggy).

HTML (self-contained): after the same render-complete wait, evaluateJavaScript("document.documentElement.outerHTML") to capture fully-rendered static HTML (Mermaid/KaTeX already expanded to SVG), then inline the CSS and (optionally) images as data: URIs. This guarantees the export matches the preview exactly and works offline, honoring the vendored-JS/no-CDN rule.

Shipping: adopt a tag-triggered GitHub Actions workflow on a macos runner: import Developer ID cert into a temp keychain → xcodebuild archive/export with Hardened Runtime → sign nested code with --options runtime --timestamp → notarize+staple the .app → create-dmg 8.1.0 → codesign the DMG → notarytool submit --wait the DMG → stapler staple → sign_update (or generate_appcast --ed-key-file) to produce the EdDSA signature → render appcast.xml using the GitHub Release body as release notes → attach DMG to the GitHub Release and publish the appcast (GitHub Pages or a raw URL that SUFeedURL points to). Use an App Store Connect API key (.p8) for notarytool, not an app-specific password. Keep the Sparkle EdDSA private key in GitHub Secrets, write it to --ed-key-file at runtime, and delete it before any commit.

Homebrew: create the self tap github.com/colophon-app/homebrew-tap with cask token colophon (brew install --cask colophon-app/tap/colophon). Use the documented stanza order; url → the versioned GitHub Release DMG; livecheck { url :url; strategy :sparkle } pointed at SUFeedURL; and — mandatory now — auto_updates true (because Sparkle self-updates). Model it on rectangle.rb. Defer submitting to homebrew-cask core until notability requirements are met.

**待决（human call）**
- PDF page geometry & UX for M1: fixed A4/Letter + default margins only, or expose a page-setup panel (NSPageLayout)? Recommend fixed Letter/A4 with a print stylesheet for M1; defer full page-setup UI.
- PDF headers/footers: confirm M1 ships WITHOUT running headers/footers (no reliable WebKit API). If page numbers are truly required, decide between buggy CSS counters vs a PDFKit/Core Graphics post-composite pass.
- Sparkle update archive format: ship the DMG as the update enclosure (simple, one artifact for both Homebrew and Sparkle) vs a separate .zip/.aar of the .app to enable Sparkle binary delta updates. Recommend DMG-only for M1 simplicity; revisit deltas if download size matters.
- Appcast hosting: GitHub Pages (clean stable SUFeedURL, needs a repo/branch) vs a raw githubusercontent URL vs the release asset. Pick one and bake into Info.plist SUFeedURL before first signed build.
- notarytool credential type in CI: App Store Connect API key (.p8, recommended, no 2FA friction) vs Apple ID + app-specific password. Confirm which secrets to provision.
- Homebrew distribution scope: self tap only for M1 (agreed in PRD §12), with submission to homebrew-cask core deferred until notability/30-day criteria are met — confirm timing.

**风险**
- Sparkle EdDSA private-key loss or leak: loss = can never ship an accepted update again; leak = attacker can sign malicious updates. Mitigate with off-machine backup + GitHub Secret only, written to --ed-key-file at runtime and deleted before commit.
- macOS 26 Tahoe print regressions: EXC_BREAKPOINT when printOp.view.frame is unset, plus general WebKit print instability. Must set frame, use runOperationModalForWindow, and test PDF export on a real macOS 26 machine (no simulator for macOS).
- createPDF single-page trap: if a contributor/AI 'simplifies' the PDF path to createPDF(), multi-page documents silently break. Encode the printOperation path (and a test on a >1-page doc) as a guardrail.
- Notarization flakiness / cert expiry in CI: Developer ID cert or ASC API key expiring, or stapler Error 65 from incompletely-signed nested code, will break releases. Sign nested binaries first; verify with spctl/stapler validate in the workflow.
- Homebrew cask lint/audit rejection: missing auto_updates true, wrong stanza order, or a livecheck that doesn't resolve. Run brew audit --cask --online and brew style before publishing; model on rectangle.rb.
- Export styling drift preview↔PDF: screen CSS and print CSS diverging so the PDF doesn't match the preview. Mitigate by sharing one stylesheet with a scoped @media print block, and by capturing outerHTML from the same rendered document.
- WebView must stay strictly downstream: an offscreen export WebView reaching back into editor state would violate the L4 'never write back' contract. Keep export as pure Model→HTML→PDF/HTML with no callbacks into DocumentModel.
- Vendored JS render-timing for export: capturing HTML/PDF before Mermaid/KaTeX finish yields half-rendered output. Need a robust render-complete signal (JS promise/flag) rather than a fixed delay.

## D13. MVP-stage predecessor failures and best practices (M1 MVP)

**执行摘要.** At the MVP stage, Markdown editors die from a small, repeatable set of causes, not from lack of features: (1) rewrite death spirals (WriteMonkey WM2→WM3, Caret 4.0 RC, HedgeDoc 2.0, Mark Text's Muya) — attempting the hard kernel too early; (2) data loss/corruption killing trust (Mark Text table/IME data-loss bugs, Laverna dying on self-built sync, and a live 2026 Obsidian forum thread where iCloud silently overwrites offline edits); (3) scope creep into IDE/PKM (Clearly built a 9-tool MCP server plus backlinks then DELETED all of it, returning to "deliberately boring"; Trilium removed multi-provider AI as an unsustainable "maintenance black hole"); (4) dependency death (Awesomium killed MarkdownPad, Qt WebKit killed CuteMarkEd, NW.js killed Haroopad, nodeIntegration security debt killed Abricotine); and (5) the TextKit-full-WYSIWYG trap (MiaoYan explicitly abandoned it, Bear built a bespoke C++/"Panda" kernel, MarkEdit chose CodeMirror 6 despite the author knowing TextKit deeply). The survivors won at the equivalent stage by being deliberately minimal and native (MarkEdit), keeping raw Markdown as the byte-exact source of truth with view-only rendering (Obsidian Live Preview on CM6), opening 94k-word files in 55ms via off-main-thread work (Bear/Panda), and building brand through typography and low-UI-cost aggregators like the merged Search+Outline omnibar and ⇧⌘P command palette (iA Writer 8, shipped 2026-06). Colophon's already-settled M1 plan — source-styling + split preview (escape hatch), byte-exact saves, folder-as-library, AST-as-seam, no AI yet — is the correct reading of this evidence. This dimension's job is to convert each failure into an enforceable M1 do/do-not and confirm the current status of every library in the plan.

**要避开的坑（前人教训）**
- Rewrite death spiral is the #1 independent-editor killer at MVP-to-next-version. WriteMonkey (WM2→WM3 rewrite drained the author, WM3 never caught up), Caret (4.0 rewrite died at RC23), HedgeDoc 2.0 (5-year rewrite still alpha), and Mark Text (58k stars could not save a burned-out single maintainer) all died on rewrites. DO-NOT: never treat M1→M2 hybrid rendering as a rewrite; it must be an additive layer on the same source-of-truth data model, with the hardest point (TextKit 2 hybrid) prototyped as an isolated spike in M1, not deferred whole to M2.　— _docs/03-windows-legacy.md; ROADMAP §7.3; https://github.com/marktext/marktext_
- Data loss = instant reputation death, and silent-overwrite-on-conflict is a LIVE 2026 failure mode, not a historical one. A current Obsidian forum thread documents iCloud silently replacing an offline-edited note with an empty version. Mark Text/Muya shipped table+IME data-loss bugs; Laverna died specifically because self-built sync lost notes across devices. DO: never silently overwrite on external change — silent reload only when the local buffer is clean, and Reload/Ignore/Compare when dirty (NSFileCoordinator/NSFilePresenter + FSEvents), and never build our own sync.　— _https://forum.obsidian.md/t/icloud-data-loss-issue-sync-conflict-handling/113584; docs/03-windows-legacy.md; architecture.md §3.3_
- Proprietary/lossy storage formats are a permanent trust tax. Boostnote's .cson lock-in was its most-cited complaint; ProseMirror/contenteditable-truth editors (Mark Text Muya, Notion, yuque Lake) lose source detail (blank lines, marker style, non-standard syntax) on roundtrip; Notable's open→closed-source pivot lost the community AND failed commercially. DO: keep the Markdown source string as the ONLY authoritative representation, AST strictly derived — this is why byte-exact save is achievable at all.　— _docs/03-windows-legacy.md; docs/05-note-apps.md; architecture.md §2.2_
- Scope creep into IDE/PKM is the modern MVP killer for this exact niche. Clearly (native Swift) built an MCP server up to 9 tools plus backlinks/tags/wiki-links, judged it off-mission, and DELETED all of it back to a 'deliberately boring' editor; its CLAUDE.md now warns to push back when tempted to add this infrastructure. Trilium removed multi-provider AI as an unsustainable maintenance black hole. Nimbalyst grew to 7+ embedded editors + terminal. DO-NOT: at M1 do NOT add backlinks, tags, RAG, embedded terminal, or any AI; keep MCP/AI as a future opt-in layer behind the AST seam.　— _docs/18-agent-editor-competitors.md (§1 Clearly); docs/13 §7.3 (Trilium); ROADMAP §1④_
- Dependency death drags the product down with it. Awesomium killed MarkdownPad (preview crashed on Win8/10), Qt WebKit's deprecation killed CuteMarkEd, NW.js aging killed Haroopad, and Abricotine died from an unfixable nodeIntegration security hole in its render process. DO: depend only on Apple-maintained, long-lived components — system WKWebView for preview/export (never headless Chrome), Apple's swift-markdown for parsing — and strictly content-isolate/sandbox the WKWebView from day one.　— _docs/03-windows-legacy.md; docs/13 §7.3 #9-10; architecture.md §6.1_
- Full inline WYSIWYG on TextKit at MVP is a proven trap that even well-funded teams avoid. MiaoYan explicitly abandoned native WYSIWYG (deemed the reliability cost too high), Bear built a bespoke cross-platform 'Panda' kernel for it, and MarkEdit's author — who explicitly knows TextKit 1 and 2 well — chose CodeMirror 6 because no native kernel competes with CodeMirror/Monaco for multi-caret and folding. Obsidian-style Live Preview is 'notoriously tricky' (cursor jumping, selection, fenced-code/table edge cases). DO-NOT: attempt inline hybrid rendering in M1; do source-styling + split preview and spike hybrid rendering in isolation.　— _docs/01-apple-native.md; https://github.com/MarkEdit-app/MarkEdit/wiki/Why-MarkEdit; https://github.com/blueberrycongee/codemirror-live-markdown_
- Single-maintainer + no revenue + perpetual beta erodes trust before features ever matter. nvUltra (7-year private beta, 'vaporware'), Yu Writer (forever Beta 0.5.3), Haroopad (forever 0.x), and Notable (features perpetually 'Future') all lost users to stagnation signals, while 2k-star ReText survived 15 years on a tiny maintenance surface. DO: ship small quarterly releases as an 'alive' signal, establish multi-maintainer governance and a sustainability mechanism (Sponsors + MAS support build) BEFORE launch, and make the open-source + local-.md promises irrevocable and public (Notable's reversal is the cautionary tale).　— _docs/01-apple-native.md; docs/03-windows-legacy.md §本类别小结; ROADMAP §7.1-7.2_

**要抄的做法（优秀实践）**
- Copy MarkEdit's minimalism and native feel: strict GFM with zero proprietary syntax, native NSToolbar/auto-dark/system controls, latest-two-macOS support only, no telemetry/server, distribution via signed .dmg + Homebrew cask. Keep AI as an OPTIONAL extension (MarkEdit-ai-writer wraps Apple Intelligence) so the core stays minimal — directly mirrors our 'AI is a seam, not a built-in' stance.　— _https://github.com/MarkEdit-app/MarkEdit; https://github.com/MarkEdit-app/MarkEdit/wiki/Why-MarkEdit_
- Copy Obsidian Live Preview's data model NOW even though we don't render inline until M2: raw Markdown in EditorState is the immutable source of truth, the syntax tree only provides token positions, and all rendering is VIEW-ONLY decoration — this is what makes copy/save/roundtrip byte-for-byte identical to a plain textarea. This is exactly architecture.md's L2 (source string truth) / L3 (derived AST) contract; adopting it in M1 means M2 hybrid rendering is a decoration layer, not a data-model change.　— _https://github.com/blueberrycongee/codemirror-live-markdown/blob/main/CODEMIRROR_LIVE_PREVIEW_DESIGN.md; architecture.md §2.2, §4.2_
- Copy Bear/Panda's large-file performance discipline (55ms to open the 94k-word Moby-Dick): parse off the main thread, lazy-load the file tree and search index (FSNotes '10k+ files smooth' is the floor), and never block typing on the full AST — high-frequency incremental highlight is decoupled from the debounced full-AST pass. Non-negotiable given the settled dual-parser architecture.　— _docs/01-apple-native.md (Bear); architecture.md §4.1-4.2_
- Copy iA Writer 8's low-UI-cost aggregators (shipped 2026-06): merge Search + Document Outline into one ⇧⌘O pane, and put formatting/export/etc behind a ⇧⌘P Command Palette. Pair with the nvUltra/FSNotes omnibar (search = create) and MiaoYan's ⌘\ split toggle. These deliver 'complete out-of-the-box' feel at near-zero interface cost — the survivor pattern for staying minimal while being useful.　— _https://9to5mac.com/2026/06/17/ia-writer-8-brings-liquid-glass-design-clear-icon-support-more/; docs/01-apple-native.md_
- Copy iA Writer's 'typography and whitespace as brand' over theme-piling: two hand-tuned light/dark themes beat a theme gallery at MVP, and using standard SwiftUI/AppKit components auto-inherits Liquid Glass on macOS 26 and falls back on 15 — a structural moat Electron cannot match. Note the 2026 reviewer consensus that Tahoe apps 'that feel right are built from scratch for it, not just an updated icon' reinforces leaning on native components and keeping the editor content area non-glass.　— _docs/01-apple-native.md; https://www.macrumors.com/2025/08/01/macos-tahoe-review/; ROADMAP §3.3_
- Copy MacMD's byte-exact Agent-file editing (turn off all smart substitution, error on non-UTF-8) and markjason's file-watch-with-no-dialog as the two zero-cost Route-B 'door' features — they deliver half the Route-B value with no AI integration, and directly serve our core user story (writing CLAUDE.md/AGENTS.md/.mdc where smart punctuation corrupts frontmatter and code fences).　— _docs/18-agent-editor-competitors.md (§5 MacMD, §2 markjason); architecture.md §3.2-3.3_

**M1 建议.** Ship M1 as the smallest thing the author will use daily, and treat "restraint" as the headline feature. Concretely for M1: (1) DO NOT attempt inline hybrid rendering — implement "source styling + marker de-emphasis" (Bear-style light render) plus ⌘\ split WKWebView preview as the escape hatch (MiaoYan pattern); hybrid rendering is an ADDITIVE M2 spike, never a rewrite (avoids the WriteMonkey/Caret/HedgeDoc spiral). (2) Adopt the Obsidian/CM6 data model literally even though M1 doesn't render inline: the Markdown source string is the single byte-exact truth, the AST is a derived value, and any future rendering is view-only decoration — this is exactly architecture.md L2/L3 and it is what guarantees byte-for-byte roundtrip. (3) Make data safety non-negotiable and testable: atomic writes, strict UTF-8 (error, never lossy-decode), preserved BOM/line-ending/trailing-newline, all five isAutomatic*Substitution flags off AND the matching NSUserDefaults registered at launch, and NO silent-overwrite on external change (Reload/Ignore/Compare when dirty; silent reload when clean) — the 2026 Obsidian iCloud thread shows silent overwrite is a live, reputation-killing failure. (4) Do the two zero-cost Route-B "door" features (MacMD's byte-exact Agent-file editing; markjason's file-watch with no "changed on disk" dialog) but ship ZERO actual AI, only the AST-as-API seam. (5) Do the low-UI-cost survivor interactions now: omnibar (search+create, nvUltra/FSNotes), ⇧⌘P command palette (iA Writer 8), ⌘\ split (MiaoYan). (6) Keep dependencies to Apple-maintained + MIT/Apache only. For the editor-kernel spike (PRD §12.4), the evidence points to fork/adopt swift-markdown-engine (Apache-2.0, v0.10.0, 833 stars, and it already bridges HighlighterSwift + SwiftMath) as the fastest path that also aligns with the M2 hybrid-rendering endgame, with CodeEditTextView (MIT) as the from-scratch-lite fallback; STTextView is disqualified as a dependency (GPL/commercial dual license) and may only be read for TextKit-2 avoidance lessons. - Editor-kernel spike (PRD §12.4): fork/adopt swift-markdown-engine (Apache-2.0, aligned with M2 hybrid endgame, but pre-1.0 + small single team — accept the fork-and-lock maintenance burden?) vs. from-scratch NSTextView+TextKit2 thin wrapper vs. CodeEditTextView (MIT) source-mode start. Evidence leans to swift-markdown-engine, but this is a human call because it commits us to tracking a pre-1.0 upstream.
- Does M1 introduce tree-sitter (Neon/SwiftTreeSitter) for source styling, or use parser-driven attribute mapping from swift-markdown until M2? Adopting swift-markdown-engine may make this moot for M1; decide during the spike.
- How much of the byte-exact/atomic-write path to test-harness at M1: the settled plan uses Data.write(.atomic) for M0, with final I/O API (NSFileCoordinator vs custom temp+rename, xattr/permission preservation) deferred to M1 — needs a decision this milestone.
- Version-history implementation (local snapshot directory vs embedded Git à la FSNotes) — deferred in architecture.md §3.5; M1 must pick one to back the eventual checkpoint-rollback.
- MAS support-build vs direct-download only for M1's first public release, given App Store sandbox limits on some system-level capabilities (the Elephas warning) — affects notarization/entitlement work now.

**风险**
- swift-markdown-engine is pre-1.0 (v0.10.0) and driven by a small single team; API churn or abandonment would hit us if we build the kernel on it. Mitigation: fork, pin, keep takeover capability, and stay able to fall back to CodeEditTextView.
- TextKit 2 remains a 'lava pool': the layoutManager silent-downgrade trap, estimated-viewport scroll jank on large files (swift-markdown-engine's non-virtualized layout mode is a concrete instance), and broken NSTextList since macOS 14. Any of these can produce the large-file jank that hurt predecessors. Mitigation: enforce the engineering.md red lines in code review; make 'large-file scroll stability' an explicit M1 acceptance test, not an aspiration.
- Byte-exact saving has many silent leak points (system substitution defaults overriding view-level flags, lossy UTF-8 decode, line-ending/BOM normalization). A single miss corrupts Agent config files — our core user story. Mitigation: byte-exact roundtrip tests already exist (recent commit); extend them to CRLF/BOM/no-trailing-newline and to the smart-substitution defaults registered at launch.
- Scope-creep gravity is strong precisely because the AST seam makes backlinks/tags/RAG/MCP feel 'easy to add'. Clearly is the cautionary case: it built all of it then deleted it. Mitigation: hold the M1 'explicitly not in MVP' line (no AI, no backlinks, no RAG, no terminal) as a governance rule, not a preference.
- Solo-developer sustainability is itself the top historical failure mode. Mitigation (already in ROADMAP §7): multi-maintainer governance, quarterly releases, and irrevocable open-source/local-.md promises published before launch.
- WKWebView preview is an attack surface if it renders untrusted Agent-produced Markdown (Abricotine died on this; the Obsidian Local REST API path-traversal CVE GHSA-62gx-5q78-wrvx is the modern version). Mitigation: strict content isolation/sandbox for the preview WebView from day one, even though MCP/HTTP exposure is a later milestone.

## 14. 内核 spike 合成（落锤）

> 由一个专门的合成 agent 消化 [D1](#d1-编辑内核起点起点-spikeabc) + [D2](#d2-textkit-2-源码语法样式化) + [D3](#d3-wkwebview-分屏预览--60fps-滚动同步) 三份最相关发现后产出。**结论进 [`decisions.md` D-M1-1](./decisions.md)，并以一次 hands-on spike 亲验落锤。**

**推荐起点.** (b) Self-built NSTextView + TextKit 2 thin wrapper — i.e. GROW the M0 kernel (Colophon/Colophon/MarkdownTextView.swift), adding swift-markdown-AST-driven source-styling and a WKWebView split preview. Explicit corollary: swift-markdown-engine (a) is NOT the M1 kernel but the M2 upstream we borrow/fork on the SAME TextKit 2 substrate. CodeEditTextView (c) is rejected as the start.

**理由.** Three grounded facts settle it. (1) M1 does not need what (a) buys. M1 is source-styling + split preview, explicitly NOT hybrid render (M1 overview 范围, architecture §4.2 note). Source-styling is just AST→NSRange attribute mapping — standard TextKit 2 that never enters the "lava pool" (custom layout fragments, marker concealment, inline widgets are all M2). docs/09 §八 prices a from-scratch FULL hybrid-render core at 6–12 person-months, but M1 needs a small fraction of that, and M0 has already delivered the wrapper (byte-exact, no .layoutManager touch, substitutions off). Adopting the whole pre-1.0, single-maintainer swift-markdown-engine as our kernel now imports its opinionated parse+geometry+marker-hiding stack (its MarkdownExtension "解析器统一管几何/标记隐藏/重排版", docs/09 §六) that we would have to reconcile against our dual-track §4.2 (tree-sitter highlight + swift-markdown semantics, both derived from the source string as sole truth, §2.2), byte-exact (§3.2, our distinctive agent-file requirement, docs/18), and model-layer undo (§5) contracts — high verification cost and the exact "依赖内核死亡" single-point risk the roadmap flags (docs/13 §七), for ZERO M1 payoff. (2) (b) does NOT box out M2. swift-markdown-engine is itself "TextKit 2 布局 + swift-cmark-lineage parse" (docs/09 §六), so at M2 we grow our thin wrapper toward it — or drop it in behind the L1/L2 seam — on the SAME foundation; that is continuous, not a rewrite (M1 overview 接口: "内核 spike 选 (a) 会让 M2 最省力" is about M2 adoption, which staying on the shared TextKit 2 substrate preserves). (3) (c) is the option that boxes us out: CodeEditTextView uses self-drawn layout that BYPASSES TextKit 2 (docs/09 §六), and it is built for code (line numbers, monospace paradigm), so choosing it makes M2 hybrid-render — which the plan builds via swift-markdown-engine's TextKit 2 path — a rip-and-replace, and fights Markdown prose along the way. Architecture §8 is explicit that "the kernel start is a replaceable implementation; these boundaries [§1–7] are the non-replaceable contract" — (b) is the smallest, already-working, red-line-clean implementation that honors that framing and keeps every M2 door open.

**spike 设计（一个人几天内跑完以确认选择）**
- Day 0 (half day) — harness + corpus. Assemble fixtures that map 1:1 to the DoD risks: Moby Dick (~1.2MB, the Bear 55ms benchmark) for perf; a real CLAUDE.md/.mdc with YAML frontmatter + code fences + smart-quote/dash traps for byte-exact; a GFM kitchen-sink (tables, task lists, footnotes, LaTeX, mermaid) for preview; a CRLF+BOM+no-trailing-newline file and a CJK/emoji file for round-trip and offset mapping. Add swift-markdown via SPM (Apache-2.0), resolve, commit Package.resolved.
- Day 1 — (b) styling slice. Extend MarkdownTextView: parse the buffer with swift-markdown OFF the main thread (§4.1), walk the AST, map each SourceRange (UTF-8 byte offsets) → NSRange (UTF-16) carefully, and apply heading size / bold weight / de-emphasized-but-PRESENT marker styling as TextKit 2 rendering attributes via NSTextContentStorage + NSTextLayoutManager — NEVER reading .layoutManager. Debounce reparse on edit. Confirm: markers stay in the source, styling shows, typing on Moby Dick holds ~60fps (debounce + background parse, no per-keystroke full reparse).
- Day 2 — (b) split preview + byte-exact + undo seam. Add ⌘\ WKWebView preview: swift-markdown → HTML (custom visitor) → loadHTMLString, with line-anchor scroll sync and a feedback-loop guard. Then run the byte-exact regression: open→noop-edit→save every corpus file, assert byte-identical (LF/CRLF, BOM, trailing newline) against the M0 MarkdownFileIO. Then prove the undo seam: route one edit intent through a stub L2 model that OWNS the UndoManager (or confirm NSTextView's built-in undo can be intercepted/mirrored into the model), demonstrating architecture §5's 'undo entry lives in the model layer' is reachable without fighting the kernel.
- Day 3 — big-doc scroll stability + (a)/(c) confirmation probes. First, stress the ONE real M1 TextKit 2 risk: viewport-estimation scroll jump on Moby Dick — scroll top↔bottom and jump to anchors, measure jitter; if it jumps, try the documented mitigations (cached fragment heights / stable scroll anchor) and record whether it stabilizes. Then two strictly time-boxed probes (≈2h each, they only guard the switch/box-out criteria, they are not builds): (a) clone swift-markdown-engine, run its demo, check for a source-only mode, verify it honors byte-exact + never touches .layoutManager + Apache-2.0, and sketch how an M2 drop-in behind our L1/L2 seam looks — output a yes/no on 'M2-via-(a) still cheap'; (c) drop CodeEditTextView into a scratch view, style a Markdown doc, and note the self-drawn-layout divergence + code-editor assumptions to confirm it is the higher M2-rewrite risk.
- Wrap — record the result in planning/M1/decisions.md and backfill architecture §8/§9 (kernel start, whether M1 introduces tree-sitter vs AST-driven attribute mapping, undo integration mode). Keep the spike branch as the M1 kernel seed if (b) passes.

**决策标准（测什么、什么情况下换）**
- STAY on (b) (expected): source-styling holds ~60fps on Moby Dick, byte-exact round-trip is green on all fixtures, an edit can be routed so the UndoManager lives in the model layer, big-doc scroll is stabilizable, and swift-markdown-engine remains a viable M2 upstream. This is the pass condition.
- SWITCH to (a) as the M1 kernel if: (b)'s AST-driven styling CANNOT reach 60fps on Moby Dick even with debounce + background parse, AND the Day-3 probe shows swift-markdown-engine does it out of the box while honoring byte-exact and the TextKit 2 red lines — i.e. the perf cost of (b) outweighs (a)'s pre-1.0 single-maintainer risk. This also collapses M1+M2 onto one engine.
- SWITCH to (c) only if: TextKit 2 viewport scroll-jump on big docs proves UNFIXABLE within the day's budget with (b), CodeEditTextView's self-drawn layout demonstrably fixes it, AND leadership accepts that M2 hybrid render will therefore also abandon TextKit 2 (paying an M2 rewrite of the swift-markdown-engine path). High bar by design.
- Hard gates that fail ANY candidate regardless of speed: touches NSTextView.layoutManager (silent TextKit 1 downgrade, §6.1), breaks byte-exact round-trip (§3.2), or forces undo out of the model layer (§5). A candidate that violates these is disqualified for M1 even if faster.

**风险与缓解**
- TextKit 2 viewport-height estimation scroll jump on large docs (the one M1 'lava' item, docs/09 §五, and a DoD acceptance item). Mitigate with cached laid-out-fragment heights and a stable scroll anchor; test explicitly on Day 3. Note this risk is NOT escaped by picking (a) — swift-markdown-engine sits on the same TextKit 2 — so the mitigation is worth banking whatever we choose.
- SourceRange (swift-markdown UTF-8 byte offsets) ↔ NSRange (UTF-16) mapping errors on multibyte content (CJK, emoji), which would corrupt styling ranges or, worse, edits. Mitigate with an explicit CJK/emoji fixture in the corpus and a mapping unit test on Day 1.
- swift-markdown-engine pre-1.0 API churn + single maintainer (the (a) risk we deliberately DEFER). Mitigate by keeping it out of the M1 kernel and behind the L1/L2 seam; when adopted at M2, fork + version-lock (architecture §8) and contribute fixes upstream (docs/09 §八).
- Over-building at M1 — drifting into syntax concealment / custom layout fragments (that IS the M2 lava pool). Mitigate by scoping the spike and M1 to attribute mapping only; concealment/inline widgets are explicitly M2 (architecture §6.2 defers the concealment state machine).
- FSEvents self-trigger / WKWebView scroll-sync feedback loops surfacing during the preview slice. Out of scope for the kernel decision but note them; guard the preview loop on Day 2 and defer the FSEvents dedup mechanism to implementation (architecture §9 item 6).

**兜底.** If the spike shows (b) cannot meet the M1 big-doc/60fps bar within budget, adopt (a) swift-markdown-engine as the M1 kernel too — run it in a source-styling mode, version-locked fork, accepting the pre-1.0 / single-maintainer risk. Because (a) shares the TextKit 2 + swift-cmark substrate, this is a lateral move on the same foundation, not a rewrite, and it collapses M1 and M2 onto one engine (the cheapest M2). (c) CodeEditTextView is the fallback of last resort — used ONLY if BOTH TextKit 2 routes ((b) and (a), which share TextKit 2) fail big-doc stability — because it costs an M2 hybrid-render rewrite of the swift-markdown-engine path and pulls the product toward a code-editor paradigm. In every fallback the §1–7 contracts (byte-exact, model-layer undo, no .layoutManager, dual-track parse, AST-as-API seam) remain the non-negotiable acceptance bar.

## 15. 完备性批判（前人没覆盖的盲区）

> 最后一道闸：一个批判 agent 通读全部发现，找**缺口 / 矛盾 / 待验证 / 额外风险 / 排期**。**这些已全部并入 [`plan.md`](./plan.md)，是本milestone最该盯的清单。**

### 缺口（M1 范围内、无人覆盖或覆盖太薄）
- AGENT-FILE RECOGNITION + SPECIAL RENDERING IS ENTIRELY UNCOVERED. PRD 5.1 section D and architecture 2.2 make 'data-driven Agent-file recognition table (CLAUDE.md/AGENTS.md/*.mdc/SKILL.md/llms.txt) + distinct rendering' a named M1 deliverable and DoD #3 item. No finding addresses detection rules (filename/glob/path), what 'special rendering' means for source-styling mode, or how it interacts with frontmatter. This is half of M1's brand identity ('leave the door for AI') and has zero research.
- THE AST-AS-API SEAM IS NOT DESIGNED. DoD #3 requires DocumentReader/DocumentEditor/ActiveEditorState boundary placeholders that COMPILE and have TESTS. Multiple findings say 'route undo through L2' and 'keep parser as pure L3 producer,' but no dimension actually specifies the seam's interface shape, method signatures, or how it maps to swift-markdown SourceRange. This is a concrete M1 code deliverable left unresearched.
- UNDO/REDO ARCHITECTURE IS UNOWNED. 'Does NSTextView keep built-in undo with the model listening, or does the model fully own undo (built-in disabled)?' appears as an OPEN DECISION in findings 5, 6, and 9, but NO dimension researches or decides it. It is the keystone that semantic shortcuts, list continuation, image paste, silent reload, and autosave all depend on — a double-undo bug surfaces everywhere if it stays unsettled. It must be a first-class output of the kernel spike, not a scattered footnote.
- FILE-TREE / SIDEBAR LAZY LOADING FOR 10k+ FILES IS MISSING. Finding 7 covers the SEARCH index thoroughly but PRD 5.1 B and architecture 2.3 also require the folder-as-library sidebar itself to lazy-enumerate directories, virtualize the tree, traverse under security scope, and track renames/moves for 10k+ files. The actual file-tree UI/data model — distinct from search — has no coverage.
- FOREGROUND-COLOR / ATTRIBUTE APPLICATION HAS NO SINGLE OWNER. Source styling (finding 2), focus dimming (finding 8), and the rubric cursor-line highlight (finding 10) all recolor text per-range, yet each proposes a DIFFERENT mechanism (content-storage delegate vs NSTextLayoutManager rendering attributes vs per-run coloring). No dimension reconciles them into one proven mechanism, so three subsystems risk three incompatible implementations of the same primitive.
- FRONTMATTER (YAML) HANDLING IS UNADDRESSED. Agent files and Obsidian vaults lean heavily on frontmatter; finding 7 reads aliases from it and finding 6 references typora-copy-images-to inside it, but no dimension owns frontmatter parsing, source-styling, or preview rendering. M1 excludes frontmatter FORMS, not basic frontmatter display.
- MULTI-DOCUMENT / WINDOW / TAB MODEL IS UNSPECIFIED. Finding 8 (FSEvents) assumes 'per open tab' presenters, but no dimension designs how multiple files open (tabs? windows?), state restoration, or the relationship between the library sidebar and open documents. This gates the per-tab-presenter decision it depends on.
- PREFERENCES/SETTINGS SURFACE + PERSISTENCE IS UNCOVERED. Theme choice, focus-mode toggles, attachment-folder rules, snapshot retention policy, font selection, and debounce windows all need a settings UI and durable storage. No dimension owns the preferences infrastructure that at least five other findings assume exists.
- ACCESSIBILITY IS ONLY PIECEMEAL. Contrast (finding 10) and Reduce Transparency (findings 8,10) are touched, but a custom TextKit-2 NSTextView needs explicit VoiceOver/accessibility exposure, Full Keyboard Access, and Dynamic Type behavior — part of the PRD's 'fully conform to macOS' requirement — with no holistic owner.
- TEST/DOGFOODING HARNESS + EXPLICIT ACCEPTANCE CRITERIA ARE UNOWNED. The entire DoD is test-gated (Moby-Dick no-dropped-frames, byte-exact CRLF/BOM/no-trailing matrix, opens an Obsidian vault, CJK search returns results), but no dimension defines the test harness, the performance-measurement method, or the pass/fail bars. Acceptance tests are named as risks in scattered findings but never consolidated into a plan.

### 矛盾（两份发现互斥，必须先统一）
- MERMAID IN/OUT OF M1. Finding 3 (preview) proposes DEFERRING Mermaid (and Shiki) out of M1 to keep the CSP tight and the bundle small. Finding 4 (GFM suite) AND PRD 5.1 explicitly keep Mermaid as a first-class M1 feature ('Mermaid: preview webview only, vendor pinned mermaid.min.js'). This is a direct scope conflict that must be resolved against the PRD, not left as an 'open decision.'
- RENDERING-ATTRIBUTE MECHANISM. Finding 2 states categorically: NEVER build on NSTextLayoutManager rendering attributes (Apple-DTS-confirmed unreliable redraw), use the NSTextContentStorageDelegate path instead. Finding 8 makes NSTextLayoutManager rendering attributes the PRIMARY mechanism for focus dimming (scrim overlay only as fallback). Finding 10 flags the same rendering attributes as 'reported unreliable' for the rubric highlight. Findings 2, 8, and 10 cannot all be right about the same API on the same stack; they must converge before any of the three subsystems is built.
- EDITOR CODE-BLOCK HIGHLIGHTING. Finding 4 adds HighlighterSwift (JavaScriptCore, whole-block re-highlight) to the EDITOR for M1 first-class fenced-code highlighting. Finding 2's source-styling architecture renders fenced code as merely 'mono + subtle background' and introduces no such dependency or JSCore cost. Unresolved: does M1 syntax-highlight the CONTENTS of editor code fences (a real dependency + perf hit finding 2 never budgeted) or not?
- PREVIEW HTML PIPELINE OPTION-SET DIVERGES. Finding 3 specifies cmark C renderer in SAFE mode with SOURCEPOS and no footnote handling; finding 4 specifies the cmark renderer with CMARK_OPT_FOOTNOTES enabled plus GFM extensions; both also float bundled markdown-it as an alternative that would be a SECOND parser diverging from the editor's cmark-gfm dialect. These must be unified into one pipeline spec, and both silently assume swift-cmark exposes its C HTML renderer publicly (see unverified claims).

### 待验证声明（动手前先核实）
- HIGHEST PRIORITY: that Apple's swift-cmark package publicly exposes cmark_render_html plus the GFM/footnote/SOURCEPOS extension C API as a usable SPM product target. Findings 3, 4, 6, and 11 (preview, GFM, image-preview, export) ALL depend on calling swift-cmark's HTML renderer directly. Apple's swift-cmark has historically vendored cmark as an internal/SPI target consumed only by swift-markdown, NOT as a public HTML-rendering product. If false, the entire preview+export pipeline must fall back to a custom MarkupVisitor or bundled markdown-it — far more work. Verify by inspecting the package's product/target visibility, not the README.
- swift-markdown-engine's load-bearing facts: that its LICENSE is actually Apache-2.0 (the research itself caught a search summary mislabeling it MIT), the v0.10.0/star-count claims, and that it 'already ships M1+M2 live source-styling with marker-hiding + caret-reveal' and 'bridges HighlighterSwift + SwiftMath.' The kernel bet rests on these; verify by reading the fork's LICENSE and source, not summaries.
- That Highlightr is now unmaintained and its README redirects to HighlighterSwift. The standards deps table still lists Highlightr as the approved M1 starter; finding 4 wants to demote it. Verify the repo's last-commit/archive status before amending standards.
- That FB9692714 (rendering-attribute redraw failure) is still open on macOS 26, AND that finding 2's NSTextContentStorageDelegate path genuinely avoids it. This single bug gates styling, focus dimming, and the rubric highlight; verify on real macOS 15 and 26 hardware.
- That swift-markdown ships with CMARK_OPT_FOOTNOTES disabled and that swift-cmark permits re-enabling it at the C level (dependent on the swift-cmark public-API claim above).
- WKWebView.printOperation gotchas on macOS 26 (must set view.frame; must use runOperationModalForWindow not runOperation; createPDF produces a single non-paginated page) and the reported macOS 26 print EXC_BREAKPOINT regression.
- That NSFileCoordinator's initWithFilePresenter self-write suppression is reliable in practice, and the replaceItemAt Cocoa-513 sporadic-failure rate on iCloud/Dropbox that finding 9 builds a retry path around.
- That Homebrew now MANDATES auto_updates true for Sparkle-updating casks, and that create-dmg 8.1.0 / Sparkle 2.8+ are the current versions with the described APIs.
- Minimum-OS reconciliation: candidates (a) swift-markdown-engine and (c) CodeEditTextView target macOS 14 while Colophon targets 15 — confirm swift-markdown-engine builds cleanly on the 15 baseline with no 14-only or 15.1-only (Writing Tools) assumptions.
- The exact CSP concessions: that KaTeX auto-render forces script 'unsafe-inline' (avoidable via renderMathInElement), that KaTeX/Mermaid force style-src 'unsafe-inline', and that Shiki's Oniguruma WASM forces 'wasm-unsafe-eval' unless the JS regex engine is used.

### 额外风险 / 单人陷阱
- SOLO-DEV SPIKE OVERLOAD. The findings collectively imply ~5 independent hard spikes: (1) kernel a-vs-b, (2) the foreground-attribute mechanism, (3) swift-cmark C-renderer availability, (4) FTS5 CJK tokenizer, (5) TextKit-2 caret-rect for typewriter. Together these are essentially the whole risk budget for one person. Each has a documented failure mode with a much-costlier fallback. They must be front-loaded as gates, not discovered mid-build.
- BYTE-EXACT REGRESSION SURFACE MULTIPLIES IN M1. 'Byte-exact done in M0' is misleading: M1 opens at least six NEW write/transform paths — atomic-replace (changing from M0's Data.write), image-drop file copy, snapshot blob writes, silent-reload re-encode, semantic-edit newline normalization, and marker de-emphasis attribute transforms. Each can silently violate the life-or-death red line. The regression suite must be EXTENDED before each path lands (CRLF/BOM/no-trailing/emoji-offset matrix), not after.
- macOS 26 REAL-HARDWARE GATE. Liquid Glass, print regressions, the dark accent, Reduce-Transparency downgrade, and FB9692714 all require a physical macOS 26 machine (no simulator). If hardware access is uncertain, theming polish, PDF export, and the signature rubric highlight all slip — this is an external dependency, not just a task.
- TWO KEYSTONE DECISIONS HAVE NO OWNER. The undo model and the foreground-attribute mechanism are each currently phrased as per-finding 'open decisions,' yet each gates 4+ downstream features. Deferring them past the kernel spike guarantees rework. Assign both as explicit spike outputs with a decisions.md entry.
- CJK SEARCH IS A SILENT TOTAL FAILURE FOR THE CORE AUDIENCE. Finding 7 correctly flags that FTS5's default tokenizer returns zero results for Chinese. This is the same severity class as byte-exact: it must be an acceptance test on a real Chinese corpus, gated before 'search is done,' not a nice-to-have.
- SCOPE-CREEP GRAVITY VIA THE AST SEAM. Finding 12's own evidence (Clearly built then deleted backlinks/MCP; Trilium cut AI) warns that the moment the AST seam exists, backlinks/tags/RAG feel 'free.' The M1 'no AI, no wiki-links, no backlinks' exclusion must be enforced as governance, because the seam makes violating it frictionless.
- PREVIEW/EXPORT SHARE ONE UNVERIFIED FOUNDATION. Because findings 3, 4, 6, and 11 all rest on the swift-cmark C-renderer assumption, a single failed verification cascades across preview, GFM rendering, in-preview image display, and HTML/PDF export simultaneously — a correlated failure, not an isolated one.

### 排期建议（→ plan.md 的 M1.x 骨架）
- PHASE 0 (D1, gates everything): run the kernel spike a-vs-b (eliminate c on architecture grounds as finding 1 argues). Bundle into this SAME gate the two decisions the kernel choice constrains and everything downstream needs fixed: (i) the undo model (built-in vs model-owned) and (ii) the AST-as-API seam signatures. Do not exit Phase 0 with these still 'open.'
- PHASE 0.5 (parallel de-risk spikes, before building any dependent feature): (a) the foreground-attribute mechanism spike — pick ONE mechanism shared by source styling, focus dimming, and the rubric cursor-line, resolving the finding 2/8/10 contradiction; (b) the swift-cmark C-renderer availability spike — this gates ALL of preview and export, so if it fails, decide MarkupVisitor vs bundled markdown-it now; (c) extend byte-exact regression tests to cover every new M1 write path before those paths are written.
- PHASE 1 (make it a daily driver ASAP — dogfooding is the DoD): source styling + Agent-file recognition table + file-tree lazy load + open/save on the final atomic-write API + autosave. This is the minimum to start eating your own dogfood; get here fast.
- PHASE 2: FSEvents + NSFileCoordinator external-change reload. Early, because it is a data-safety/trust path, shares the atomic-write plumbing from Phase 1, and its self-write dedup underpins the later snapshot store.
- PHASE 3: semantic shortcuts + list continuation + image paste + URL auto-link — all gated on the Phase 0 undo model; do not start before it is settled.
- PHASE 4: split preview + 60fps scroll sync — gated on the Phase 0.5b pipeline decision. Ships Mermaid+KaTeX+code highlight per PRD (resolve the finding-3 defer-Mermaid contradiction toward the PRD).
- PHASE 5: omnibar + FTS5 content search (CJK tokenizer as a hard acceptance gate) + command palette (separate stably-ordered list, not pooled).
- PHASE 6: focus mode + typewriter scrolling — gated on the Phase 0.5a mechanism decision plus the TextKit-2 caret-rect spike.
- PHASE 7: filesystem version history/snapshots — builds on the Phase 1 atomic write and Phase 2 self-write dedup.
- PHASE 8: two-theme polish + HTML/PDF export (export gated on Phase 0.5b) — needs macOS 26 hardware.
- PHASE 9 (M1 close): release automation + Sparkle + Homebrew. Caveat: generate and OFF-MACHINE-BACKUP the Sparkle EdDSA key at the very START of M1 (not here), and bake SUFeedURL into Info.plist before the first signed build, even though the release workflow itself lands last.
